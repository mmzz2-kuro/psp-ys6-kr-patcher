## 1차 인게임 확인과 계획 보완

사용자 확인 결과 한글 대사는 출력되지만 ASCII `,`, `.`, `?`, `!`가 한글보다 좁은 단일바이트 문자 폭으로 렌더링된다. 이 때문에 문장부호의 글꼴 인상이 다르고 `바람이..?`에서 `이`와 마침표가 지나치게 붙어 보인다.

원인은 한글 글리프의 두께가 아니라 다음과 같이 판정한다.

- 한글: 새로 배정한 2바이트 전각 폰트 레코드와 전각 advance 사용
- 현재 문장부호: 기존 ASCII 단일바이트 글리프와 반각 advance 사용

다음 보정을 추가한다.

1. ASCII 쉼표·물음표·느낌표를 게임에 이미 있는 대응 전각 CP932 문장부호로 변환한다.
2. 연속 마침표 `...`와 `..`는 게임 원문이 사용하는 전각 말줄임표 `…` 조합으로 정규화한다.
3. 일반 마침표가 단독으로 필요한 경우에는 전각 마침표 코드와 화면 폭을 별도로 확인한다.
4. 문장부호 뒤 ASCII 공백은 문맥에 따라 전각 공백 또는 불필요한 공백 제거로 통일한다.
5. 변환 전후의 표시 문자열과 원시 바이트를 보고서에 기록하고 사용자 번역 원문 자체는 보존한다.
6. 보정 ISO에서 쉼표, 말줄임표, 물음표와 느낌표의 간격을 다시 인게임 확인한다.

## 1단계: 번역 작업공간 백업 및 대상 고정

- `translations.json`의 현재 SHA-256을 기록한다.
- 작업 폴더에 변경 전 백업을 만든다.
- 대상은 정확히 동일한 ISO 경로의 문자열 인덱스 35~43으로 제한한다.
- 9개 레코드의 원문 HEX와 SHA-256을 실제 원본 XSO와 다시 비교한다.
- 사용자가 입력한 번역문을 별도의 019 빌드 입력 JSON으로 복사해 전체 작업공간의 다른 레코드와 분리한다.

## 2단계: 줄바꿈과 상태 정규화

원문에 게임 줄바꿈 토큰 `\n`이 있는 인덱스 37, 39, 41을 처리한다.

- 번역문에 입력된 실제 줄바꿈 문자 1개를 게임 토큰 문자 두 개 `\n`으로 변환한다.
- 원문의 `\n` 개수와 번역문의 정규화된 `\n` 개수가 같은지 검증한다.
- 줄바꿈이 없는 다른 6개 번역문은 실제 줄바꿈과 `\n` 토큰을 모두 허용하지 않는다.
- 원문에 없는 제어 토큰과 마크업이 추가되지 않았는지 확인한다.
- 검증을 통과한 9개 빌드 입력 레코드만 `reviewed`로 전환한다.

전체 `translations.json`의 상태는 자동으로 일괄 변경하지 않는다. 019 빌드용 입력과 사용자가 편집하는 정본의 동기화 방식은 결과 문서에 기록한다.

## 3단계: 문자 집합과 코드 매핑 확장

- 정규화된 9개 번역문에서 공백과 게임 제어 토큰을 제외한 고유 문자를 첫 등장 순서로 수집한다.
- 기존 016 매핑 10개와 `한 → 0x98FC`를 유지한다.
- 기존 매핑에 없는 한글과 필요한 문장부호만 고유·미사용 안전 슬롯에 추가한다.
- ASCII 쉼표, 마침표, 물음표, 느낌표와 공백은 게임의 기존 1바이트 코드를 우선 사용하고 새 폰트 슬롯을 배정하지 않는다.
- 한글은 각 2바이트 게임 코드로 인코딩한다.
- 매핑 중복, 원본 사용 코드 충돌 및 미지원 문자를 검사한다.

현재 `ys6_hangul_codec.py`의 인코더는 한글 매핑과 전각 공백만 처리하므로 ASCII·제어 토큰을 안전하게 통과시키도록 확장할 가능성이 높다.

## 4단계: 사용자 번역용 EBOOT 생성

- 복호화 원본 EBOOT를 기준으로 기존 10자와 새 한글 글리프를 함께 적용한다.
- 글꼴은 `C:/Windows/Fonts/gulim.ttc`, Gulim Regular, 12px를 사용한다.
- 게임 형식은 16×12, 1bpp, 글리프당 24바이트다.
- 안전 가시 폭 12px 자동 보정을 적용한다.
- 계획 015에서 검증한 `한` 수동 패턴은 유지한다.
- 빈 글리프, 우측 잘림 및 매핑·레코드 불일치를 검사한다.
- EBOOT 변경은 배정된 글리프의 24바이트 비트맵 범위로 제한한다.

## 5단계: 9개 문자열 일괄 재조립

- 문자열별 원본 길이, 번역 길이와 증감량을 기록한다.
- 모든 뒤쪽 상대 오프셋을 누적 증감량에 따라 재계산한다.
- 명령 영역, 문자열 개수, 문자열 인덱스 및 대상 외 원시 문자열을 보존한다.
- 재조립 결과를 재파싱하고 각 대상 문자열의 원시 바이트를 매핑으로 역검증한다.
- 인덱스 44 이후 문자열의 원시 바이트가 원본과 동일한지 확인한다.

## 6단계: 압축 및 할당 용량 판정

- 수정 XSO를 zlib 레벨 9로 압축한다.
- `.z` CRC32, 비압축 크기, zlib EOF 및 payload 왕복을 검증한다.
- 런타임 아카이브 `s_0551.bin`의 `s_0551.xso.z` 기존 할당 2,048바이트와 비교한다.

판정:

- 2,048바이트 이하: 기존 할당 영역 안에서 교체하고 계속 진행
- 2,048바이트 초과: 아카이브를 재배치하거나 확장하지 않고 즉시 중단

초과 시 실제 필요 크기, 초과량, 다음 엔트리 위치와 아카이브 재배치 범위를 문서화해 별도 계획으로 사용자 확인을 받는다.
