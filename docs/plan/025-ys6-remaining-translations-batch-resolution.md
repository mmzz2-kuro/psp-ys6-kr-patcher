# Ys VI 미적용 번역 자동 대응 및 일괄 누적 빌드 계획

## 상태

- 계획 작성: 완료
- 사용자 확인: 대기
- 구현: 미착수
- 정적 검증: 미착수
- 인게임 검증: 미착수
- 결과 문서: `/docs/result/025-ys6-remaining-translations-batch-resolution.md`

## 배경

018~024에서 대사 추출, 번역 작업공간, 한글 코드·글리프 생성, XSO 재조립, 아카이브 flags `0x01000000`·`0x41000000`, standalone 직접 로드, 구조 변형 XSO 대응 및 누적 ISO 빌드를 구현했다.

초기에는 실제 로드 규칙을 밝히기 위해 `s_0551`, `AdolSleep`, `OruhaMove`, `AskOruha`를 개별적으로 추적했다. 그 과정에서 다음 유형이 확인됐다.

1. standalone과 아카이브 XSO가 동일 payload인 경우
2. 아카이브의 일반 데이터 엔트리
3. flags `0x41000000` 보조 데이터 엔트리
4. 게임이 standalone 사본을 직접 읽는 경우
5. 동일 메뉴가 이름과 구조가 다른 별도 XSO에 복제된 경우

이제 번역을 하나씩 별도 이슈와 ISO로 처리하는 대신, 번역 작업공간 전체를 입력으로 받아 대응 가능한 번역을 일괄 분류·검증·빌드하는 파이프라인이 필요하다.

현재 024 최종 ISO에 포함된 검수 번역은 63개다. 사용자 번역 정본에는 아직 적용되지 않은 번역이 19개 경로, 22개 남아 있다.

| 유형 | 경로 수 | 번역 수 |
|---|---:|---:|
| `s_0000/talkkebin` | 1 | 3 |
| `s_0000/talktokusa` | 1 | 2 |
| `s_hidden1` 인물명 XSO | 17 | 17 |
| 합계 | 19 | 22 |

## 목표

1. 번역 작업공간 전체에서 번역이 작성된 레코드를 자동 수집한다.
2. 이미 누적 빌드에 포함된 번역과 신규 미적용 번역을 자동으로 구분한다.
3. 각 standalone XSO를 실제 런타임 아카이브 또는 standalone 직접 로드 대상으로 대응한다.
4. 원문과 XSO 구조가 확정된 변형에는 명시적 전파 규칙을 생성한다.
5. 모호한 후보는 자동 적용하지 않고 검토 목록으로 분리한다.
6. 확정된 모든 번역을 한 번에 사전 빌드하고 누적 ISO 하나를 생성한다.
7. 이후 번역 추가 시 동일 파이프라인을 반복 실행할 수 있게 한다.

## 기본 원칙

- 번역문을 자동 생성하거나 교정하지 않는다.
- 사용자 번역 정본의 번역·상태·메모를 수정하지 않는다.
- 파일명이 같다는 이유만으로 번역을 전파하지 않는다.
- 문자열 하나가 같다는 이유만으로 런타임 대상을 확정하지 않는다.
- 모호한 후보보다 미적용 상태가 안전하다.
- 원본 ISO에서 매번 누적 결과를 다시 생성하고 패치 ISO를 연쇄 수정하지 않는다.
- 확인된 대응 규칙은 기계 판독 가능한 파일로 남겨 다음 빌드에서 재사용한다.

## 1단계: 전체 번역 인벤토리

번역 작업공간과 현재 누적 검수본을 비교해 다음 상태를 생성한다.

- `already_applied`: 현재 누적 검수본에 동일 경로·인덱스·번역으로 존재
- `new_exact_source`: 신규 번역이며 원본 경로와 raw SHA-256 일치
- `source_changed`: 원문 또는 raw SHA-256 불일치
- `empty`: 번역 없음
- `duplicate_conflict`: 같은 논리 대상에 서로 다른 번역 존재
- `invalid_tokens`: 제어 토큰 또는 마크업 불일치

산출물:

- `translation-inventory.json`
- `translation-inventory.csv`
- 적용·제외·오류 개수 요약

현재 예상:

- 이미 적용: 63개
- 신규 후보: 22개

실제 결과가 다르면 사용자 번역이 추가되거나 바뀐 것으로 보고 현재 값을 정본으로 다시 집계하되, 계획 범위가 크게 변하면 확인을 요청한다.

## 2단계: XSO 대응 후보 자동 생성

신규 번역이 속한 각 standalone XSO에 대해 전체 카탈로그와 v2 런타임 대응표를 검색한다.

### 비교 신호

- 전체 XSO payload SHA-256 일치
- 압축 컨테이너 SHA-256 일치
- XSO 문자열 수와 인덱스 구조
- 번역 대상 원문 완전 일치
- 대상 앞뒤 문자열 일치
- 분기 식별자와 명령 문자열 순서
- 문자열 집합의 포함 관계
- XSO 코드·명령 영역 해시 또는 정규화 구조 해시
- 파일명과 맵 계열
- 아카이브 index·name·flags

### 후보 등급

- `exact_payload`: XSO payload가 완전히 동일
- `exact_structure`: 코드·분기 구조와 대상 문자열이 완전히 대응
- `exact_context`: 대상 및 충분한 앞뒤 문맥이 완전히 대응
- `partial_structure`: 일부 구조만 일치해 검토 필요
- `text_only`: 원문 문자열만 일치해 자동 적용 금지
- `unresolved`: 후보 없음

## 3단계: 자동 적용 판정

다음 항목만 자동 적용 후보로 인정한다.

### A. 동일 payload

- standalone과 런타임 XSO SHA-256이 동일
- 원문 인덱스와 raw SHA-256 동일
- 기존 v2 대응 상태가 exact one-to-one 또는 검증된 duplicate

### B. 명시적으로 검증된 구조 대응

- 표시 문자열과 분기 식별자 순서가 모두 일치
- 대응 인덱스가 1:1
- 각 대상 원문이 완전히 일치
- 규칙 파일에 source·target 경로와 인덱스 쌍을 기록
- 최초 규칙 생성은 사용자 확인 필요

### C. standalone 직접 교체

- 원본 standalone payload가 번역 source XSO와 일치
- 수정 컨테이너가 기존 ISO 할당 이내
- 경로가 명시적 적용 목록에 포함

다음은 자동 적용하지 않는다.

- 파일명만 같은 후보
- 인물명 문자열 하나만 일치하는 후보
- 앞뒤 구조가 다른 `talk*` 변형
- 하나의 source가 여러 target에 서로 다른 문맥으로 대응
- 런타임 증거가 없고 사용 여부를 판정할 수 없는 파일

## 4단계: 대응 규칙 파일

확정 대응을 코드에 하드코딩하지 않고 별도 JSON으로 관리한다.

예상 경로:

- `/tools/scripts/data/ys6_translation_routes.json`

예상 내용:

- 스키마 버전
- source ISO 경로
- source XSO SHA-256
- target 유형: archive, standalone 또는 양쪽
- target runtime key와 standalone 경로
- 대응 방식: 동일 payload 또는 구조 전파
- source·target 문자열 인덱스 쌍
- 원문 SHA-256
- 승인 상태와 관련 작업 번호
- 비고

규칙 로딩 시 현재 원본과 하나라도 맞지 않으면 해당 규칙을 비활성화하고 오류로 보고한다.

## 5단계: 미적용 22개 일괄 분석

### `talkkebin` 3개

- 전체 `talkkebin` 변형에서 대상 원문과 주변 문자열을 비교한다.
- 메뉴·분기 식별자 및 코드 구조를 함께 검사한다.
- 실제 맵에서 사용되는 런타임 아카이브 후보와 standalone 후보를 분리한다.
- 구조가 다른 변형으로 무차별 전파하지 않는다.

### `talktokusa` 2개

- 전체 `talktokusa` 변형과 아카이브 대응을 같은 방식으로 조사한다.
- 번역 대상 인덱스와 문맥이 완전히 일치하는 후보만 확정한다.

### `s_hidden1` 인물명 17개

- 동일 압축·payload 복사본이 있는 `s_9000`, `s_9002` 후보는 exact로 분류한다.
- 구조가 다른 `s_9000`, `s_9002`, `s_9012`, `s_0550` 후보는 인물명 주변 역할과 명령 구조를 비교한다.
- 인물명 하나만 같은 경우에는 자동 전파하지 않는다.
- 실제 사용 여부가 불명확하면 검토 또는 대표 표본 런타임 확인 대상으로 남긴다.

## 6단계: 검토 보고서와 사용자 확인

ISO 생성 전에 다음 세 목록을 제공한다.

1. 자동 적용 확정 목록
2. 구조 대응 승인 필요 목록
3. 미확정·제외 목록

각 행에는 다음을 포함한다.

- 번역 source 경로·인덱스·원문·번역
- target 경로·runtime key·target 인덱스
- 대응 등급과 근거
- 아카이브 flags 및 할당 크기
- standalone 동시 교체 여부
- 위험 또는 미확정 사유

구조 대응이나 범위 확장이 하나라도 있으면 사용자 확인 전에는 ISO를 생성하지 않는다.

## 7단계: 검수 입력 자동 생성

사용자가 승인한 확정 목록만 기존 024 검수본에 추가한다.

- 실제 줄바꿈을 게임 `\n` 토큰으로 정규화
- 제어 토큰·마크업 검증
- source와 target raw SHA-256 검증
- 구조 전파는 승인된 인덱스 쌍만 허용
- 빈 번역과 미확정 후보 제외
- 최종 검수 레코드와 제외 레코드를 별도 보고

사용자 번역 정본은 변경하지 않는다.

## 8단계: 전체 사전 빌드

024의 왼쪽 정렬 한글 글리프 설정을 유지한다.

- 굴림 렌더 크기 12픽셀
- 16×12 1비트 셀
- 한글 bbox 왼쪽 시작점 `x=1`
- 수동 `한` 글리프 포함
- 확인용 atlas 확대는 `Image.Resampling.NEAREST`로 통일

전체 승인 번역 문자 집합으로 다음을 수행한다.

- 글리프 슬롯 확장
- EBOOT 재생성
- 모든 대상 XSO 재조립
- 압축 컨테이너 무결성 검사
- 아카이브 및 standalone 할당 검사
- 대상별 여유 공간 보고

하나라도 초과하거나 검증에 실패하면 전체 ISO 생성은 중단한다.

## 9단계: 누적 ISO 생성 및 정적 검증

원본 ISO에서 승인된 모든 대상을 한 번에 교체한다.

- EBOOT
- 확정 아카이브 작업본
- 확정 standalone 직접 로드 파일

검증:

- 예상 교체 개수와 실제 개수 일치
- 각 아카이브 크기 유지
- 각 ISO extent LBA 유지
- 수정 XSO 재추출 해시 일치
- 모든 번역 원시 바이트 역검증
- 대상 외 아카이브 엔트리 보존
- 허용 extent와 길이 필드 밖 변경 0건
- 원본 ISO와 024 ISO SHA-256 유지
- 자동 테스트 및 Python 컴파일 통과

## 10단계: 인게임 묶음 검증

모든 대상을 파일마다 메모리 추적하지 않는다.

- exact payload 유형 대표 이벤트
- 구조 전파 유형 대표 이벤트
- standalone 직접 로드 유형 대표 이벤트
- 인물명 표시 대표 화면
- 기존 `s_0551`, `AdolSleep`, 오르하 이벤트 회귀

문제가 발생한 유형만 정적 대응과 런타임 로드를 재조사한다. PPSSPP 진단 설정 변경은 별도 승인이 필요한 예외 단계로 둔다.

## 중단 및 재확인 조건

- 사용자 번역 수가 계획 기준과 크게 달라짐
- 기존 적용 번역과 신규 번역이 충돌함
- 제어 토큰·마크업 불일치
- 동일 원문이 서로 다른 의미·문맥 후보에 존재함
- 구조 대응 인덱스가 1:1이 아님
- 원본 payload 또는 raw SHA-256 불일치
- 런타임 후보가 여러 개이며 우선순위를 확정할 수 없음
- 수정 컨테이너가 기존 할당을 초과함
- 글리프 슬롯 부족
- 아카이브 재배치 또는 ISO extent 이동이 필요함
- 실행 코드 패치가 필요함
- 대상 외 데이터가 변경됨
- 인게임 이벤트 진행이 손상됨

## 후속 작업

025가 완료되면 번역 추가 작업은 다음 반복 절차로 단순화한다.

1. 사용자가 GUI에서 번역 추가
2. 전체 resolver 실행
3. 자동 확정·검토 필요 목록 확인
4. 승인된 전체 번역 사전 빌드
5. 누적 ISO 하나 생성

이 파이프라인이 안정화된 뒤 사용자용 GUI 패치 도구에 번역 검증·대응 보고서·누적 빌드 기능을 연결한다.
