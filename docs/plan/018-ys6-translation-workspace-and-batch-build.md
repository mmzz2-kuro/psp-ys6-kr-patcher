# Ys VI 번역 작업공간 및 다중 문자열 일괄 빌드 계획

## 상태

- 계획 작성: 완료
- 사용자 확인: 대기
- 구현: 완료
- 정적 검증: 완료
- GUI 검증: 완료 — 번역·상태·메모 편집 및 저장 확인
- 인게임 검증: 완료 — 연속 2개 대사와 후속 이벤트 정상

## 중간 진행 결과

- 전체 카탈로그 7,424개 레코드의 번역 JSON/CSV 작업공간 생성
- 원문 SHA-256 동기화, 충돌·고아·중복 키 및 토큰·마크업 검증 구현
- 기존 GUI에 번역문·상태·메모 편집 및 JSON 저장 기능 추가
- 검수 상태 번역만 적용하는 다중 문자열 XSO 빌더 구현
- `s_0551` standalone XSO와 런타임 아카이브 XSO payload SHA-256 일치 확인: `1BA1D501FEF350045691CA15F3A4F99205623C829F3B916FEA566E3978175614`
- 인덱스 35: 22→26바이트, `한글출력테스트입니다입니다`
- 인덱스 36: 16→12바이트, `테스트입니다`
- XSO 전체 크기 증감: 0바이트
- 수정 `.xso.z`: 1,957바이트, 기존 할당 여유 91바이트
- 단위 테스트: 50개 통과
- 원본 대비 허용 범위 밖 ISO 변경: 0건
- PoC ISO: `/patched/018-translation-batch-poc/Ys VI - translation-batch-poc.iso`
- PoC ISO SHA-256: `3E43F6ACBB8C1B9DFD961E85DF5804144031A8B29E92F4D33CC1B2DB271CB681`
- 사용자가 PPSSPP에서 첫 번째·두 번째 시험 대사와 이후 이벤트의 정상 진행을 확인했다.
- 사용자가 GUI의 번역 편집·저장 동작을 확인했다.
- GUI에 UTF-8 BOM CSV 내보내기와 원문 SHA-256 검증 기반 가져오기를 추가했다.

## 배경

계획 010에서 1,194개 XSO의 문자열 7,424개를 대사·화자·선택지 등으로 분류한 카탈로그와 GUI 열람 도구를 만들었다. 계획 016에서는 한글 코드 매핑과 다중 글리프 생성 기반을 검증했고, 계획 017에서는 XSO 문자열의 바이트 길이를 변경해도 뒤쪽 오프셋을 재계산하여 다음 대사까지 정상 실행됨을 확인했다.

현재 남은 문제는 번역문을 어떤 형식으로 관리하고, 여러 문자열에 반복 가능하게 적용하며, 필요한 한글 글리프와 아카이브 용량을 빌드 전에 어떻게 검증할지다. 수작업으로 XSO 인덱스와 HEX를 입력하는 방식은 전체 7,424개 문자열에 사용할 수 없으며 번역 원문이 바뀌어도 알아채기 어렵다.

## 이번 단계의 목표

1. 원문과 번역문을 함께 보존하는 번역 작업공간 형식을 정한다.
2. 기존 대사 GUI에서 번역문을 입력·수정·저장할 수 있게 한다.
3. 번역 파일의 원문 해시, 문자열 인덱스 및 역할을 검증한다.
4. 번역문에 필요한 한글·기호 집합을 자동 산출한다.
5. 016 코드 매핑과 폰트 빌드를 번역 문자 집합에 맞춰 확장한다.
6. 하나의 XSO 안에 있는 여러 문자열을 한 번에 가변 길이로 재조립한다.
7. 수정 XSO를 압축하고 기존 아카이브 할당 공간에 들어가는지 빌드 전에 보고한다.
8. 작은 다중 문자열 PoC를 PPSSPP에서 검증한다.

## 중요한 범위 구분

이번 단계는 “번역 작업공간과 일괄 빌드 체계”를 만드는 작업이다. 게임 전체의 실제 한국어 번역을 생성하는 단계가 아니다.

- PoC 번역문은 구조 검증용으로 명확히 표시한다.
- 원문의 의미를 임의로 완성 번역하지 않는다.
- 사용자가 나중에 작성하거나 검수한 번역문을 같은 형식으로 넣을 수 있게 한다.
- 기존 아카이브 할당을 넘는 파일은 목록으로 보고하고 빌드를 중단한다.
- 아카이브 전체 재배치는 다음 별도 계획으로 분리한다.

## 원본 및 결과물 보호

- 원본 ISO `/roms/Ys VI - Napishtim no Hako (Japan).iso`는 읽기 전용으로 취급한다.
- 성공한 016·017 ISO는 변경하지 않는다.
- 번역 작업공간과 분석 자료는 `/.work/ys6-translation-workspace`에 둔다.
- 사용자 GUI는 `/tools/ys6_dialogue_viewer.py`를 확장하거나 `/tools`에 별도 Python GUI로 작성한다.
- 비GUI 빌드·검증 도구는 `/tools/scripts`에 둔다.
- PoC ISO는 `/patched/018-translation-batch-poc`에 최종본 한 개만 둔다.
- 중간 ISO는 `/.work`에 만들고 검증 후 삭제한다.
- 게임 원본 데이터, 번역 전 임시 XSO 및 복호화 EBOOT는 Git에 포함하지 않는다.

## 1단계: 번역 작업공간 스키마

UTF-8 JSON을 정본으로 사용하고 스프레드시트 편집용 UTF-8 BOM CSV를 함께 지원한다.

문자열별 필수 필드:

| 필드 | 의미 |
|---|---|
| `iso_path` | 원본 XSO의 ISO 경로 |
| `map_group` | 맵 그룹 |
| `map_id` | 맵 ID |
| `xso_name` | XSO 이름 |
| `string_index` | XSO 내부 문자열 인덱스 |
| `roles` | dialogue·speaker·choice 등 역할 |
| `source_text` | 일본어 원문 |
| `source_raw_hex` | 원문 원시 바이트 |
| `source_sha256` | 원문 바이트 해시 |
| `translation` | 한국어 번역문 |
| `status` | 미번역·초벌·검수·제외 상태 |
| `notes` | 번역자 메모 |

고유 키는 `iso_path + string_index`로 한다. 같은 표시 문자열이 여러 위치에 있어도 별도 레코드로 유지한다.

## 2단계: 원문 동기화 및 변조 감지

기존 `dialogue_catalog.json`에서 번역 작업공간을 생성하거나 갱신한다.

- 새 원문은 미번역 상태로 추가
- 기존 키의 번역문·상태·메모는 보존
- 원문 바이트가 바뀌면 자동 적용하지 않고 충돌 상태로 표시
- 사라진 원문은 삭제하지 않고 고아 레코드로 보고
- 중복 키, 잘못된 인덱스, 누락 필드 및 잘못된 HEX 거부
- JSON↔CSV 왕복 시 한글, 줄바꿈 토큰 및 마크업 보존

## 3단계: GUI 번역 편집

기존 `/tools/ys6_dialogue_viewer.py`를 다음 방향으로 확장한다.

- 기존 검색·필터·원문 열람 기능 유지
- 번역문 입력 영역
- 상태 선택: 미번역, 초벌, 검수, 제외
- 이전·다음 레코드 이동 및 저장
- 원문과 번역문의 문자 수·게임 바이트 수 표시
- 제어 토큰과 마크업 누락 경고
- 현재 필터의 번역 진행률 표시
- JSON 작업공간 열기·저장
- CSV 내보내기·가져오기

GUI는 파일 편집만 담당하고 ROM이나 ISO를 직접 수정하지 않는다. 실제 빌드는 검증 가능한 비GUI 스크립트가 수행한다.

## 4단계: 번역 검증

비GUI 검증기는 다음을 검사한다.

- 번역 상태가 `검수`인 레코드만 빌드 대상으로 선택
- 빈 번역, 미지원 문자 및 매핑 누락
- 원문의 `\n`, `\s`, `\xN` 토큰 보존 여부
- `<color:...>`, `<ruby:...>`, `<endruby>`, `<scale:...>` 마크업 보존 여부
- 문자열 안의 NUL 금지
- 게임 코드 인코딩 후 바이트 길이
- XSO별 원본·수정 문자열 풀 크기 차이
- `.z` 재압축 후 예상 또는 실제 크기
- 아카이브 엔트리 할당 초과 여부

경고와 오류를 구분하고, 오류가 하나라도 있으면 EBOOT·아카이브·ISO를 생성하지 않는다.

## 5단계: 번역 문자 집합과 폰트 빌드

- 빌드 대상 번역문에서 고유 한글과 필요한 기호를 첫 등장 순서로 수집한다.
- 기존 `한 → 0x98FC` 및 016에서 검증한 매핑은 유지한다.
- 새 문자는 고유·미사용 안전 슬롯에 결정론적으로 추가한다.
- 매핑 CSV/JSON과 EBOOT가 일치하는지 검증한다.
- Gulim 12px, 16×12 1bpp 및 안전 가시 폭 12px 규칙을 적용한다.
- 빈 글리프와 우측 잘림 가능성을 오류로 보고한다.
- 수동 패턴 재정의 기능을 유지한다.

PoC에 필요한 문자만 추가하며 전체 2,136개 후보를 미리 선점하지 않는다.

## 6단계: 다중 문자열 XSO 재조립

`ys6_xso.py`의 내부 재조립 기능을 재사용하여 한 XSO에 여러 교체 항목을 한 번에 적용한다.

- 교체 목록은 문자열 인덱스와 인코딩된 원시 바이트로 구성
- 중복 문자열 인덱스 거부
- 길이 증가·감소 혼합 지원
- 모든 상대 오프셋 재계산
- 명령 영역과 문자열 개수·인덱스 보존
- 대상 외 문자열 원시 바이트 보존
- 수정 전후 XSO 크기와 누적 증감량 보고
- 수정 XSO 재파싱 및 번역 매핑 역검증

기존 단일 `replace` CLI는 유지하고, 배치 명령이나 별도 스크립트를 추가한다.

## 7단계: 런타임 아카이브 대응 조사

카탈로그의 `data/map/.../*.xso.z` 경로와 실제 런타임 `data/arc/*.bin` 내부 엔트리를 연결해야 한다.

- ISO의 `/PSP_GAME/USRDIR/data/arc` 파일 목록을 읽기 전용으로 조사
- 각 아카이브의 내부 파일명 목록과 크기·할당 공간 수집
- `map_group`, `map_id`, `xso_name`을 기준으로 카탈로그 XSO와 아카이브 엔트리 대응
- 이름이 중복되거나 대응이 불명확한 항목은 자동 적용 금지
- standalone map XSO와 runtime arc XSO의 원본 payload 해시 비교
- 대응 결과를 CSV/JSON으로 기록

계획 013에서 확인한 `s_0551.bin → s_0551.xso.z` 대응은 기준 표본으로 사용한다.

## 8단계: 다중 문자열 PoC

첫 실행 경로에서 확인 가능한 같은 XSO의 문자열 2개 이상을 선택한다.

- 하나는 계획 017의 첫 대사
- 하나는 그 다음에 실제로 표시되는 대사 또는 같은 이벤트의 후속 문자열
- 두 문자열의 길이는 원문과 다르게 설정해 증가·감소가 함께 발생하도록 구성
- PoC 문구는 테스트임을 명확히 하고 기존 016 글리프를 최대한 재사용

정확한 인덱스와 문구는 XSO 명령 참조와 인게임 순서를 확인한 뒤 계획 문서에 기록한다. 새 인게임 경로 탐색이 필요하면 사용자에게 도달 지점을 안내한다.

## 9단계: PoC 빌드 및 검증

빌드 파이프라인:

1. 번역 작업공간 검증
2. 필요한 문자 집합과 코드 매핑 생성
3. 다중 글리프 EBOOT 생성
4. 대상 XSO 다중 문자열 재조립
5. `.z` 재압축·CRC32 검증
6. 기존 할당 공간 검사
7. 런타임 아카이브 교체
8. 원본 ISO에서 PoC ISO 생성
9. 내부 파일 재추출 및 전체 diff 검증

검증 항목:

- 두 번역문이 매핑을 통해 정확히 역변환됨
- 두 문자열 이후의 대사·이벤트 정상 진행
- 아카이브와 ISO 기존 할당 범위 밖 변경 0건
- 원본 ISO SHA-256 유지
- 전체 단위 테스트 및 Python 바이트코드 컴파일 통과

## 완료 조건

- 번역 JSON/CSV 스키마와 원문 동기화 규칙이 구현된다.
- GUI에서 번역문·상태·메모를 편집하고 저장할 수 있다.
- 원문 변경, 토큰·마크업 누락 및 미지원 문자를 빌드 전에 검출한다.
- 빌드 대상 번역문에서 필요한 글리프와 매핑을 자동 생성한다.
- 한 XSO의 여러 문자열을 한 번에 가변 길이로 재조립한다.
- 카탈로그 XSO와 런타임 아카이브 엔트리의 대응 근거가 기록된다.
- 할당 초과 항목은 ROM을 만들기 전에 정확히 보고하고 중단한다.
- 두 개 이상의 시험 번역문과 후속 이벤트가 PPSSPP에서 정상 동작한다.
- 중간 ISO가 정리되고 결과 문서가 작성된다.

## 중단 및 재확인 조건

다음 중 하나가 발생하면 구현을 중단하고 계획을 갱신한 뒤 사용자에게 다시 확인받는다.

- 카탈로그 XSO와 런타임 아카이브의 대응을 안전하게 결정할 수 없음
- PoC 수정 `.xso.z`가 기존 아카이브 할당을 초과함
- 아카이브 내부 파일 오프셋 이동 또는 아카이브 크기 증가가 필요함
- ISO 파일 재배치가 필요함
- 문자열 인덱스 추가·삭제 또는 명령 스트림 수정이 필요함
- 폰트 안전 슬롯이 PoC 문자 집합에도 부족함
- 실행 코드 패치가 필요함
- GUI가 원문 게임 데이터나 ISO를 직접 수정해야만 작업을 수행할 수 있음
