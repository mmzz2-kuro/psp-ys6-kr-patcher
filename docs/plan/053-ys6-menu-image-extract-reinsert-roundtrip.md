# 053. Ys VI 메뉴 이미지 리소스 추출·재삽입 왕복 검증

## 상태

- 대상 화면 및 실제 런타임 리소스 식별 완료
- 추출·재압축·통합 아카이브 재삽입 검증 완료
- PSP DXT1 좌표 표식의 PPSSPP 출력 확인 완료
- 결과 문서 작성 완료

## 배경

시스템 설정 화면의 하단 안내 문구는 EBOOT의 동적 텍스트로 한글화됐지만, 다음 중앙 메뉴 글자는 별도의 글꼴과 그림자·질감을 사용한다.

- `BGMのボリューム`
- `効果音のボリューム`
- `標準に戻す`
- `キーコンフィグ`
- `操作説明`
- `タイトル画面に戻る`

이 글자들은 메뉴 배경 또는 버튼 텍스처에 합성된 이미지일 가능성이 높다. 과거 조사에서 `PSP_GAME/USRDIR/data/menu/optionbg00.dds.z`~`optionbg02.dds.z`가 관련 후보로 확인됐지만, 실제 글자 포함 여부와 안전한 재삽입은 검증하지 않았다.

## 목표

1. 시스템 설정 화면을 구성하는 정확한 ISO 이미지 리소스를 식별한다.
2. `.dds.z` 압축을 해제하고 DDS 이미지를 정상적으로 확인 가능한 PNG로 변환한다.
3. DDS의 포맷·알파·밉맵·크기를 보존한 채 다시 생성할 수 있는지 확인한다.
4. 재압축한 `.dds.z`를 원래 ISO 할당 공간 및 로딩 구조에 맞게 재삽입할 수 있는지 확인한다.
5. 무변경 왕복과 시각적 표식 왕복을 구분해 검증한다.
6. 검증된 경로를 이후 GUI 이미지 한글화 기능에 연결할 수 있도록 문서화한다.

## 작업 절차

### 1. 관련 리소스 식별

원본 ISO에서 다음 후보를 우선 조사한다.

- `PSP_GAME/USRDIR/data/menu/optionbg00.dds.z`
- `PSP_GAME/USRDIR/data/menu/optionbg01.dds.z`
- `PSP_GAME/USRDIR/data/menu/optionbg02.dds.z`
- 같은 디렉터리의 option·config·help 관련 DDS/MIG 리소스
- 필요하면 `data/arc/*.bin`에 포함된 동일 이름 또는 메뉴 관련 엔트리

각 파일에 대해 ISO LBA, 원본 크기, 할당 크기, 압축 방식, 압축 해제 크기 및 SHA-256을 기록한다.

#### 런타임 사용본 추가 확인

PPSSPP의 깨끗한 텍스처 덤프에서 설정 화면 아틀라스가 독립 `optionselect.dds.z` 수정과 무관하게 원본 상태로 로드되는 것을 확인했다. 원본 DXT 블록 조각을 ISO 전체에서 검색했을 때 다음 패키지에도 완전한 사본이 있었다.

- 비사용 후보 ISO 경로: `PSP_GAME/USRDIR/data/image/_static_tex.dds.z`
- 원본 컨테이너 크기: 664,433바이트
- ISO 할당 크기: 665,600바이트
- 압축 해제 payload 크기: 2,379,788바이트
- 내장 optionselect DXT3 시작 오프셋: `0x106120`
- 내장 DXT3 크기: 65,536바이트
- 독립 optionselect DXT3와 일치: 65,536/65,536바이트

초기 분석에서는 MIG 파일 기준 DXT 시작을 `0x80`으로 계산했으나, 이미지 섹션 오프셋을 중복 가산한 오류였다. 실제 독립 MIG의 DXT 시작은 `0x70`이며, 이에 대응하는 `_static_tex` 시작은 `0x106120`이다. v5 표식이 나오지 않은 원인은 이 16바이트(4×4 블록 한 개) 오프셋 오류로 기록한다.

v6에서 독립 파일과 `_static_tex.dds.z`를 정확한 오프셋으로 함께 수정했지만 PPSSPP의 깨끗한 텍스처 덤프와 실제 화면에는 표식이 나타나지 않았다. 따라서 `_static_tex`의 완전 사본도 런타임 사용본이 아니며 이 가설은 폐기한다.

PPSSPP 텍스처 덤프명 `0900efd0000008086fc71ec8.png`의 PSP 주소 `0x0900EFD0`를 기준으로 실행 중 메모리를 조사했다. 옵션 화면 진입 후에만 확인되는 65,536바이트 DXT3 아틀라스를 추출·렌더링한 결과, 다음을 포함한 256×256 합성 아틀라스임을 확인했다.

- 옵션 메뉴 조각 두 벌
- Yes/No 등 확인 UI 조각
- 아이템·장비 스프라이트

런타임 DXT 고유 조각을 수정 ISO의 모든 파일과 `.z` 해제 payload에서 역검색한 결과 실제 저장 위치는 밑줄이 없는 별도 파일이다.

- 실제 ISO 경로: `PSP_GAME/USRDIR/data/image/static_tex.dds.z`
- 원본 컨테이너 크기: 665,135바이트
- 압축 해제 payload 크기: 2,347,020바이트
- 런타임 256×256 DXT3 아틀라스 시작 오프셋: `1,073,456` (`0x106130`)

v7 표식 검증에서는 `static_tex.dds.z`의 해당 아틀라스만 수정한다. 합성 아틀라스 안에 옵션 조각이 두 벌 있으므로 두 조각의 `効果音のボリューム` 행에 같은 16×16 표식을 넣어 선택 상태와 비선택 상태 어느 쪽을 사용해도 확인되게 한다. 선택된 DXT3 블록 밖의 해제 payload가 동일한지 검증하고, 재압축본이 기존 ISO 할당 범위 안에 드는지 확인한다.

v7 실행 메모리 검사에서는 수정 마젠타 블록이 0건이고 원본 런타임 블록이 8건 발견됐다. 원본 `static_tex.dds.z` 압축 컨테이너 조각을 ISO에서 다시 검색해 다음 통합 아카이브 사본을 확인했다.

- 아카이브: `PSP_GAME/USRDIR/data/arc/init.bin`
- 엔트리: index 29, `static_tex.dds.z`
- 아카이브 내부 오프셋: `0x89000` (561,152)
- 엔트리 원본 크기: 665,135바이트
- 엔트리 할당 크기: 665,600바이트

게임은 개별 `data/image/static_tex.dds.z`보다 `init.bin` 내부 사본을 우선 사용한다. v8은 원인 분리를 위해 원본 ISO의 `init.bin` 내부 엔트리만 같은 표식 컨테이너로 교체한다. 최종 빌드 경로에서는 standalone과 `init.bin` 사본을 동일하게 유지한다.

v8에서 표식은 출력됐지만 `효과음`이 아니라 `표준으로 되돌리기` 행에 격자로 나타났다. 저장 DXT 블록 인덱스와 PPSSPP 덤프 좌표를 대조한 결과 이 아틀라스의 65,536바이트 저장 레이아웃은 `256×256` 선형이 아니라 `128×512`이며, 한 행은 64블록이 아니라 32블록이다. v9에서는 두 사본으로 오인했던 좌표를 제거하고 `128×512` 기준 `x=40..55`, `y=28..43`에 해당하는 16개 블록만 수정한다.

v9에서는 표식 위치가 `효과음` 행으로 이동했지만 정사각형이 아니라 네 개의 세로 줄무늬로 출력됐다. 이 결과를 다시 대조해 `128×512`는 행 이동만 설명한 중간 가설이며, 실제 논리 텍스처는 `256×256`이고 64블록 행을 PSP의 8행 단위로 스위즐한다는 것을 확인했다. v10은 논리 블록 `(x, y)`를 다음 저장 인덱스로 변환한다.

`stored = (y // 8) * (64 * 8) + x * 8 + (y % 8)`

미리보기에서도 같은 공식을 역으로 적용해 저장 블록을 논리 `256×256` 배열로 되돌린 뒤 렌더링한다.

다만 v10 사전 미리보기에서 이 공식으로 원본 전체가 정상 복원되지 않아 표식 ISO 생성을 보류했다. 최종 좌표 변환은 추정식 대신 블록 ID 진단으로 확정한다. 4,096개 저장 DXT 블록 각각을 블록 인덱스가 포함된 고유 RGB565 단색으로 바꾼 진단 아틀라스를 `init.bin`에 넣고, PPSSPP가 덤프한 256×256 이미지에서 각 4×4 블록의 색을 다시 인덱스로 복원한다. 이 한 번의 진단으로 저장 블록과 출력 좌표의 전체 순열표를 작성한 뒤 실제 표식 및 한글 이미지를 삽입한다.

v10 블록 맵 덤프에서 출력의 짝수 블록은 넣은 ID가 정확히 나타나고 홀수 블록은 투명해졌다. 이는 16바이트 DXT3 블록으로 보았던 데이터가 런타임에서는 8바이트 PSP DXT1 블록 두 개로 해석된다는 것을 증명한다. 두 번째 8바이트의 `FF` 값은 DXT1의 동일 endpoint와 color index 3 조합이 되어 투명 블록으로 출력됐다.

최종 런타임 조건은 다음과 같이 정정한다.

- 포맷: PSP DXT1, 블록당 8바이트
- 논리 크기: 256×256
- 블록 행 폭: 64
- 사용 범위: `static_tex.dds` payload `0x106130..0x10E12F` (32,768바이트)
- 저장 인덱스: `block_y * 64 + block_x` (선형)

v11은 `효과음`의 논리 좌표 `x=40..55`, `y=28..43`에 대응하는 DXT1 블록 16개만 마젠타로 교체한다.

### 2. 압축 해제와 이미지 확인

기존 `.z` 컨테이너 처리기를 우선 재사용한다.

- 8바이트 헤더 구조 확인
- zlib payload 압축 해제
- DDS 헤더, 가로·세로 크기, FourCC/픽셀 포맷, 밉맵 수 확인
- 알파 채널을 유지한 PNG 미리보기 생성
- 각 이미지가 화면의 어느 부분과 대응하는지 이미지 및 알파를 대조

분석용 비GUI 스크립트는 `/tools/scripts`에 작성하고 산출물은 `.work/ys6-menu-image-roundtrip/`에 둔다.

### 3. 무변경 왕복 검증

압축 해제한 원본 DDS를 수정하지 않고 다시 `.dds.z`로 만든다.

- 재압축 파일을 다시 해제했을 때 DDS payload가 원본과 완전히 같은지 확인
- 원본과 재압축본의 컨테이너 헤더 비교
- 재압축 크기가 ISO 파일의 할당 공간 이내인지 확인
- 관련 파일이 아카이브 내부에도 중복 저장됐는지 확인

무변경 왕복은 DDS 인코더를 거치지 않으므로 압축 컨테이너 처리 자체를 검증한다.

### 4. DDS 편집 왕복 검증

글자가 포함된 것으로 확정된 이미지 한 장의 복사본에 작고 명확한 테스트 표식을 추가한다.

- 원본 해상도 유지
- 원본 DDS 압축 포맷 유지
- 알파 채널 유지
- 기존 밉맵이 있으면 동일한 수로 재생성하거나 포맷 요구사항을 확인
- DDS → PNG → 테스트 표식 → DDS 변환
- 변환한 DDS가 다시 열리고 예상 픽셀이 유지되는지 확인

실제 일본어 글자를 지우거나 한글 문구를 제작하는 것은 이번 왕복 검증 범위에 포함하지 않는다.

#### PSP DXT3 좌표 보정

`optionselect.dds.z`는 PC DXT3와 블록 내부 바이트 순서가 다르며, 이미지 데이터의 첫 4×4 블록 때문에 평면 디코딩 결과가 한 블록 밀린다. 편집 좌표와 게임 좌표를 일치시키기 위해 다음 대칭 변환을 적용한다.

- 추출: PSP→PC DXT3 블록 내부 순서 변환 후 전체 4×4 블록 스트림을 `+1` 순환 이동
- 삽입: 편집된 PC DXT3 블록 스트림을 `-1` 순환 이동한 뒤 PC→PSP 블록 내부 순서 변환
- 변경하지 않은 블록은 원본 MIG 바이트를 유지하고, 표식과 겹치는 블록만 교체

표식은 작은 점 대신 실제 사용 영역의 16×16 사각형으로 만들고 다음 값을 JSON 보고서에 기록한다.

- 편집 PNG 좌표와 사각형
- 변경된 논리 DXT 블록 좌표·번호
- 대응하는 저장 DXT 블록 번호와 MIG 파일 오프셋
- 원본 MIG, 편집 PNG, 역변환 MIG, `.dds.z`, 테스트 ISO의 SHA-256

### 5. 테스트 ISO 재삽입

시각적 표식이 있는 리소스를 원본과 별도의 테스트 ISO에만 삽입한다.

- 원본 ISO는 읽기 전용 유지
- `/patched/053-menu-image-roundtrip/` 아래 좌표 보정 테스트 ISO 생성
- 원본 ISO 파일 레코드와 할당 영역을 벗어나지 않는 제자리 교체 우선
- 파일 크기가 바뀌면 ISO9660의 LE/BE 데이터 길이 필드를 함께 갱신
- 파일 바로 뒤의 다른 ISO 데이터가 변하지 않았는지 검증
- 중복 리소스가 있으면 필요한 모든 사본을 같은 테스트 ISO에서 함께 교체
- `_static_tex.dds.z` 재압축본이 기존 665,600바이트 할당 범위 안에 드는지 확인
- 내장 DXT3 대상 범위 밖 payload가 원본과 동일한지 확인
- v7에서는 실제 사용본 `static_tex.dds.z`만 교체하고, `optionselect.dds.z`와 `_static_tex.dds.z`는 v6 실패 원인 분리를 위해 원본 상태로 둔다.

ISO 생성 전에 preflight로 크기와 대상 경로를 검증한다.

### 6. PPSSPP 화면 검증

사용자가 테스트 ISO로 시스템 설정 화면에 진입해 다음을 확인한다.

- 테스트 표식이 예상 위치에 출력되는가
- 메뉴 전환 상태별 이미지가 올바르게 바뀌는가
- 투명도·색상·블렌딩이 깨지지 않는가
- 크래시·검은 텍스처·깨진 밉맵이 없는가

표식이 확인되면 해당 리소스의 추출·편집·재삽입 경로를 확정한다.

표식이 보이지 않으면 PPSSPP 텍스처 덤프의 실제 사용 해시와 실행 메모리의 원본·수정 블록 존재 여부를 차례로 확인하여 로딩 경로를 추적한다.

사용자가 직접 이미지를 편집하는 GUI 기능은 왕복 경로가 확인된 뒤 별도 계획으로 추가한다.

## 검증 기준

1. 대상 화면의 일본어 글자가 포함된 이미지 파일을 시각적으로 확인한다.
2. 무변경 `.dds.z` 왕복 후 DDS SHA-256이 원본과 일치한다.
3. DDS 편집본의 해상도·포맷·알파·밉맵 조건이 원본과 일치한다.
4. 재압축본이 할당 공간을 넘지 않는다.
5. 테스트 ISO에서 대상 외 영역이 변경되지 않는다.
6. PPSSPP에서 표식이 출력되고 메뉴가 정상 작동한다.
7. 원본 ISO는 변경되지 않는다.

## 제외 범위

- 시스템 설정 이미지의 최종 한글 디자인 제작
- 모든 메뉴 이미지의 일괄 번역
- 사용자 GUI 이미지 편집기
- 검증되지 않은 파일의 무차별 ISO 삽입

## ROM 처리

- 원본 ISO는 절대 수정하지 않는다.
- 테스트 ISO는 정확한 대상 리소스가 확정되고 preflight가 통과한 뒤 한 개만 생성한다.
- 작업 종료 시 테스트 ISO의 용도와 삭제 가능 여부를 결과 문서에 기록한다.
