## 배경

023에서 flags `0x41000000` 보조 아카이브 XSO, 명시적 standalone 교체, `s_0203/AskOruha` 선택지 대응을 구현하고 인게임 한글 출력을 확인했다.

사용자가 번역 작업공간의 다음 파일에 초반 오르하 이벤트 대사를 일부 추가했다.

- `PSP_GAME/USRDIR/data/map/s_02/s_0203/oruhamove.xso.z`
- 전체 문자열: 21개
- 현재 번역: 12개
- 번역 인덱스: 2, 3, 4, 5, 7, 8, 9, 10, 11, 12, 13, 14

사전 읽기 전용 검사에서 번역 12개의 줄바꿈 토큰과 `\x1` 제어 토큰은 원문과 일치했다. 이번 단계는 작성된 12개만 적용하고 나머지 문자열을 임의로 번역하지 않는다.

## 목표

1. `s_0203/OruhaMove`의 사용자 번역 12개를 별도 검수 입력에 추가한다.
2. 기존 023 최종 번역 51개를 모두 유지한다.
3. `s_0203/OruhaMove`의 아카이브 및 standalone 사본을 함께 수정한다.
4. 기존 할당 범위 안에서 누적 ISO를 생성한다.
5. PPSSPP에서 번역 출력과 이벤트 진행을 확인한다.

## 적용 범위

신규 번역 대상:

- index 2: `あら……？`
- index 3: `きゃっ……！`
- index 4: `ご、ごめんなさい。`
- index 5: 기도를 시작하면 주변이 보이지 않는다는 대사
- index 7–14: 아돌의 회복 상태, 오르하 자기소개 및 섬에 온 경위 질문

제외:

- 번역이 비어 있는 index 0, 1, 6, 15, 16, 17, 18, 19, 20
- `s_0203`의 다른 XSO 신규 번역
- 번역문 교정·윤문
- 번역 정본의 상태 변경
- GUI 도구 연결

## 1단계: 검수 입력 준비

023 최종 검수 입력 51개를 기준으로 `s_0203/OruhaMove`의 번역이 있는 12개만 복사한다.

검증:

- 경로와 문자열 인덱스
- 원문 raw SHA-256
- 실제 줄바꿈을 게임 `\n` 토큰으로 정규화
- `\x1` 및 기타 제어 토큰 보존
- ruby와 color 등 마크업 보존
- 중복 키 없음
- 빈 번역 제외

예상 최종 검수 레코드는 63개다. 실제 개수가 다르면 빌드를 중단하고 원인을 확인한다.

## 2단계: 런타임 대상 확인

- standalone: `PSP_GAME/USRDIR/data/map/s_02/s_0203/oruhamove.xso.z`
- 아카이브: `PSP_GAME/USRDIR/data/arc/s_0203.bin`
- 엔트리: `OruhaMove.xso.z`

## 1차 인게임 결과 및 자간 보정 계획

사용자가 신규 `s_0203/OruhaMove` 대사의 한글 정상 출력을 확인했다. 다만 같은 문장 안에서 일부 글자가 붙고 일부 글자가 떨어져 보이는 자간 불균일이 발견됐다.

### 원인 분석

- 게임 폰트 레코드는 문자 코드 2바이트와 16×12 비트맵 24바이트로 구성되며 글리프별 advance 필드는 없다.
- 한글은 모두 기존 CP932 전각 코드 슬롯을 사용하므로 게임 측 진행 폭은 동일하다.
- 현재 글리프 생성기는 굴림 12px 렌더 결과의 오른쪽이 12픽셀을 넘을 때만 왼쪽으로 이동한다.
- 글리프의 자연 폭과 좌측 bearing은 정규화하지 않는다.
- 024 글리프 182개의 실제 잉크 폭 분포는 9픽셀 70개, 10픽셀 62개, 11픽셀 47개, 12픽셀 3개다.
- 화면에 나온 문장 글리프의 좌측 시작점도 0–3픽셀로 다르다. 예를 들어 `저`는 bbox `[3,0,12,11]`, `작`은 `[1,0,12,11]`, `하`는 `[0,0,12,11]`이다.
- 따라서 전각 셀 간격은 같지만 셀 내부 좌우 여백 합이 문자 조합마다 달라져 시각적 자간이 불균일하다.

### 보정 범위

1. 원본 굴림 렌더 결과를 글자별 자연 좌표로 사용하지 않고, 잉크 bbox를 기준으로 수평 정규화한다.
2. 글리프를 훼손하지 않는 범위에서 공통 목표 폭과 좌우 여백 규칙을 적용한다.
3. 9–12픽셀인 현재 글리프를 무조건 늘려 획을 왜곡하지 않는다. 우선 동일 셀 안에서 중심 정렬하고, 필요할 때만 최근접 이웃 방식의 제한적 폭 조정을 비교한다.
4. 기존 수동 `한` 글리프는 정상 출력이 확인됐으므로 별도 기준으로 유지하거나 같은 시각 중심에 맞춘다.
5. 문장부호는 기존 CP932 전각 글리프를 사용하므로 이번 보정에서 비트맵을 교체하지 않는다.
6. 보정 전·후 atlas와 다음 대표 문자열의 시뮬레이션 이미지를 생성해 비교한다.
   - `저, 기도를 시작하면`
   - `주위가 보이지 않아서……`
7. 사용자가 비교안을 확인한 뒤에만 EBOOT와 024 ISO를 다시 생성한다.

### 추가 중단 조건

- 중심 정렬만으로 자간이 개선되지 않고 획 너비 조정이 필요함
- 폭 조정으로 한글 획이 뭉개지거나 오른쪽 잘림이 재발함
- 기존에 정상 확인한 `한` 또는 문장부호가 나빠짐

자간 보정은 EBOOT 전체 한글 글리프의 외형을 바꾸므로 중요한 범위 변경이다. 사용자 확인 전에는 글리프 생성 코드나 ISO에 적용하지 않는다.

### 자간 보정안 사용자 확인

- 모든 한글 글리프의 실제 bbox 왼쪽을 `x=1`에 맞추는 비교안을 생성함.

- 사용자가 해당 비교 이미지를 확인하고 새 ISO 적용을 승인함.
- 기존 024 ISO를 보존하고 왼쪽 정렬 EBOOT를 사용하는 별도 검증 ISO를 생성한다.
