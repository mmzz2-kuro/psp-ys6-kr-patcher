## 배경

계획 015에서 다음 경로를 실제 게임으로 검증했다.

- PPSSPP가 ISO 내부의 복호화 ELF `EBOOT.BIN`을 직접 실행할 수 있다.
- 실행 파일의 폰트 테이블은 4,608개의 26바이트 레코드로 구성된다.
- 각 레코드는 2바이트 CP932 코드와 16×12 1bpp 글리프 24바이트를 가진다.
- 사용되지 않던 코드 `0x98FC`에 `한`을 배정하고 첫 대사에 같은 코드를 넣어 정상 출력했다.
- 자동 생성된 Gulim 글리프는 오른쪽 획이 실제 표시 영역에서 잘릴 수 있으며, 안전 영역으로 좌표를 보정해야 한다.

단일 글리프 경로는 확인됐지만 전체 한글 패치에는 문자별 코드 배정표, 다수 글리프 생성기, 충돌 검사 및 반복 가능한 EBOOT 패치 절차가 필요하다.

## 이번 단계의 목표

이번 016 작업은 전체 대사 번역이 아니라, 번역 데이터를 안전하게 수용할 수 있는 폰트·인코딩 기반을 만드는 단계다.

1. 원본 폰트의 전체 코드와 게임 데이터에서 실제 사용하는 CP932 코드를 조사한다.
2. 보존 코드와 한글 전용으로 재사용 가능한 코드 슬롯을 구분한다.
3. 한글 문자↔게임 2바이트 코드 매핑 파일 형식을 정한다.
4. 여러 한글 글리프를 Gulim에서 일괄 생성하고 실제 가시 폭에 맞게 배치하는 도구를 만든다.
5. 매핑 충돌, 잘림 가능성, 빈 글리프 및 EBOOT 변경 범위를 자동 검증한다.
6. 대표 한글 여러 글자를 첫 대사에 넣은 ISO로 PPSSPP 인게임 출력을 확인한다.

## 범위에서 제외하는 작업

- 전체 일본어 대사의 한국어 번역
- 번역문 전체 삽입
- 가변 길이 대사 재배치 또는 XSO 명령 구조 변경
- 메뉴·이미지·영상 자막의 한글화
- 정식 펌웨어 PSP용 EBOOT 재암호화·재서명
- 11,172개 현대 한글 음절을 전부 내장하는 작업

실제 번역문에 필요한 문자 집합은 번역 단계에서 확정한다. 이번 단계에서는 도구 검증에 필요한 대표 문자 집합만 사용하고, 이후 확장 가능한 매핑 구조를 만든다.

## 1단계: 코드 슬롯 사용 현황 조사

복호화 EBOOT의 폰트 테이블 4,608개 레코드에서 다음을 산출한다.

- 레코드 인덱스, CP932 코드, 원문 문자 및 글리프 존재 여부
- 중복 코드와 디코딩 불가능 코드
- 추출된 전체 XSO 문자열 7,424개에서 각 코드의 사용 횟수
- 대사, 화자명, 시스템성 문자열 등 현재 분류별 사용 여부
- 폰트에는 있지만 추출 문자열에서 사용되지 않은 코드
- ASCII, 숫자, 구두점, 제어 표현 및 UI 호환을 위해 보존해야 할 코드

XSO 외부의 메뉴·실행 파일 문자열 때문에 단순히 “대사에서 0회”인 코드를 곧바로 안전하다고 판정하지 않는다. ISO 내 문자열 검색과 실행 파일 참조 가능성을 함께 기록하고, 확실한 미사용 슬롯과 번역 완료 후 재사용 가능한 일본어 슬롯을 구분한다.

## 2단계: 한글 코드 매핑 규칙

매핑 파일은 사람이 검토할 수 있는 UTF-8 CSV를 정본으로 하고, 자동 처리용 JSON을 함께 생성한다.

필수 필드:

| 필드 | 의미 |
|---|---|
| `unicode` | 한글 문자의 Unicode 코드 포인트 |
| `character` | 사람이 읽는 문자 |
| `game_code` | 게임 문자열에 넣을 2바이트 코드 |
| `font_index` | EBOOT 폰트 레코드 인덱스 |
| `original_character` | 교체 전 CP932 문자 |
| `original_usage_count` | 원본 추출 문자열의 사용 횟수 |
| `status` | 보존·예약·PoC 배정·번역용 배정 상태 |

규칙:

- 한 글자에는 하나의 게임 코드만 배정한다.
- 같은 게임 코드를 여러 한글에 중복 배정하지 않는다.
- 원본에서 사용 중인 코드는 기본적으로 자동 배정하지 않는다.
- 코드 바이트에 `0x00`이 포함되거나 XSO 문자열 종료·명령 해석과 충돌할 가능성이 있는 값은 제외한다.
- 배정 순서는 실행마다 달라지지 않도록 결정론적으로 고정한다.
- 기존 `한 → 0x98FC` 배정은 호환성을 위해 유지한다.

## 3단계: 실제 글리프 가시 영역 확인

계획 015의 화면 결과를 토대로 16×12 저장 셀과 실제 렌더러의 가시 폭 차이를 다시 확인한다.

- `0x0882CFFC` 글리프 렌더링 루틴의 폭·클리핑 계산을 정적으로 재검토한다.
- 원본 일본어 글리프의 사용 픽셀 경계와 화면 표시를 비교한다.
- 오른쪽 안전 여백과 허용 가능한 최대 x 좌표를 수치로 확정한다.
- 추정값을 코드에 고정하지 않고 분석 결과와 근거를 보고서에 기록한다.

실제 가시 폭을 안전하게 입증할 수 없으면 여러 x 위치의 시험 글리프를 한 번에 출력하는 캘리브레이션 PoC를 먼저 수행한다.

## 4단계: 다중 글리프 생성 도구

Python 비GUI 스크립트를 `/tools/scripts`에 작성하거나 기존 폰트 도구를 확장한다.

예상 기능:

- UTF-8 문자 목록 또는 매핑 CSV 입력
- `C:/Windows/Fonts/gulim.ttc`, Gulim Regular, TTC 인덱스 0 사용
- 16×12 1bpp 게임 글리프 생성
- 확정된 가시 영역 안으로 바운딩 박스 자동 이동
- 원본 코드값과 레코드 순서를 유지한 채 비트맵 24바이트만 교체
- 수정 전후 EBOOT 해시 및 변경 오프셋 보고
- 전체 및 변경 글리프 아틀라스 PNG 생성
- 문자별 픽셀 경계, 빈 글리프, 우측 잘림 가능성 보고
- 필요 시 문자별 수동 16×12 패턴 재정의 지원

Gulim 글꼴 파일 자체는 결과물이나 저장소에 복사하지 않는다. 렌더링된 1bpp 비트맵만 EBOOT에 포함한다.

## 5단계: 대표 문자 집합 PoC

전체 한글 음절을 임의로 넣지 않고 다음 성격을 포함하는 작은 대표 집합을 사용한다.

- 이미 검증된 `한`
- 가로·세로 모음 조합
- 받침 없음·홑받침·복잡한 받침 형태
- 좌우 폭이 넓거나 오른쪽 획이 긴 음절
- 실제 한글 패치 안내문에 사용할 수 있는 짧은 문구의 문자

대표 문구와 정확한 코드 배정은 1단계의 안전 슬롯 수를 확인한 뒤 계획 문서에 기록한다. 기존 첫 대사 22바이트 범위에서 가능한 같은 길이 시험 문자열을 우선 사용한다.

## 6단계: EBOOT 및 대사 패치

- 계획 015에서 덤프한 복호화 EBOOT를 기준으로 대표 글리프를 일괄 적용한다.
- 수정은 배정된 레코드의 각 24바이트 비트맵 범위로 제한한다.
- 첫 대사에는 매핑표를 통해 인코딩한 대표 한글 코드를 적용한다.
- XSO 문자열은 기존과 같은 길이를 우선하며 `.z` CRC32, 압축 해제 크기와 아카이브 할당 범위를 검증한다.
- 길이 유지가 불가능하면 XSO 재배치나 실행 코드 변경을 하지 않고 중단 조건에 따른다.

## 7단계: PoC ISO 생성 및 검증

원본 ISO에서 다음 두 파일만 교체한 PoC ISO를 생성한다.

1. `PSP_GAME/SYSDIR/EBOOT.BIN`
2. `PSP_GAME/USRDIR/data/arc/s_0551.bin`

검증 항목:

- 원본 및 결과 ISO 크기·SHA-256
- 두 내부 파일의 재추출 SHA-256
- 폰트 매핑과 EBOOT 레코드의 일치
- 대사 바이트와 매핑 CSV의 역변환 일치
- 원본 대비 허용 범위 밖 변경 0건
- 단위 테스트와 Python 바이트코드 컴파일 통과
- PPSSPP 완전 재시작, 새 게임, ISO 단독 실행
- 대표 한글이 누락·오인·우측 잘림 없이 표시됨
