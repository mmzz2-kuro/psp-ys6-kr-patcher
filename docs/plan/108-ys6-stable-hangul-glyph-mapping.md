# 108. Ys VI 한글 글리프 매핑 영구 고정 및 세이브 호환 계획

상태: 완료

## 목적

- 번역에 새 한글이 추가돼도 이미 배정된 `한글 문자 → 게임 코드 → 폰트 인덱스` 관계가 절대 바뀌지 않게 한다.
- 이전 패치 ISO로 만든 세이브에 저장된 한글 코드가 새 패치에서 다른 글자로 보이는 문제를 방지한다.
- 신규 문자는 기존 매핑 뒤의 안전한 미사용 슬롯에만 추가하는 append-only 정책을 적용한다.

## 확인된 원인

- 현재 영구 자료인 `seed-mapping.json`에는 192개 매핑만 고정돼 있다.
- 현재 전체 빌드는 약 978개 문자를 사용한다.
- `extend_mapping`은 seed에 없는 필요한 문자를 현재 번역 텍스트의 등장 순서대로 수집하고, 폰트 인덱스가 높은 미사용 슬롯부터 다시 배정한다.
- 새 문자가 기존 문자보다 앞에서 처음 등장하면 이후 동적 배정 문자들의 코드가 밀릴 수 있다.
- 세이브 데이터에는 한글 자체가 아니라 게임 코드가 저장되므로, 새 EBOOT에서 같은 코드가 다른 글리프를 가리키면 저장된 명칭이 깨진다.

## 1. 호환 기준 매핑 확정

- 102번에서 정상 동작이 확인된 테스트 ISO의 EBOOT와 당시 생성된 글리프를 기준으로 현재 978개 매핑을 교차 검증한다.
- 현재 `work/current/mapping.json`, 102번 보관 EBOOT와 폰트 비트맵 SHA-256을 대조해 문자·코드·인덱스 관계를 복원한다.
- 불일치가 있으면 임의로 현재 매핑을 채택하지 않고 다음 자료를 비교한다.
  - 기존 seed 192개
  - 보관된 패치 ISO 또는 EBOOT
  - 최근 빌드 manifest와 글리프 보고서
- 기존 세이브와 호환될 기준을 하나의 canonical mapping으로 확정하고 근거 해시를 기록한다.

## 2. 영구 매핑 파일

- 작업용 `work/current/mapping.json`을 기준 자료로 사용하지 않는다.
- `/tools/patchdata` 아래에 버전 관리되는 ULJM-05009 전용 canonical 한글 매핑 파일을 둔다.
- 각 레코드에 다음 값을 보존한다.
  - Unicode 문자
  - 게임 코드
  - 폰트 인덱스
  - 원본 일본어 문자와 원본 사용량
  - 최초 배정 상태 또는 매핑 버전
- 매핑 파일에는 schema version과 mapping revision을 기록한다.

## 3. Append-only 배정 정책

- 기존 문자의 게임 코드와 폰트 인덱스는 어떤 경우에도 자동 변경하거나 제거하지 않는다.
- 새 번역에서 미등록 문자를 발견하면 canonical mapping을 그대로 복사한 뒤 안전한 미사용 슬롯에만 추가한다.
- 신규 문자 배정 순서는 번역 파일의 순서와 무관하게 결정론적으로 처리한다.
- 권장 방식은 신규 문자 Unicode 코드포인트 정렬 후 안전 슬롯 순서대로 추가하는 것이다.
- 한 빌드에서 추가된 신규 매핑은 자동 생성 보고서로만 끝내지 않고 canonical mapping 갱신 대상으로 명시한다.
- canonical mapping 파일이 갱신되지 않은 상태에서 새 문자를 조용히 임시 배정하지 않는다.

## 4. 검증 및 실패 조건

- 다음 오류가 있으면 사전 검증과 빌드를 중단한다.
  - 같은 문자에 여러 코드가 배정됨
  - 같은 코드 또는 폰트 인덱스에 여러 한글이 배정됨
  - 기존 canonical 레코드의 코드·인덱스 변경
  - 사용 중인 일본어 슬롯과 충돌
  - 폰트 테이블 원본 코드 불일치
  - 신규 문자에 사용할 안전 슬롯 부족
- canonical mapping SHA-256과 revision을 preflight와 build manifest에 기록한다.
- 빌드 결과의 EBOOT 글리프 보고서가 canonical mapping과 완전히 일치하는지 확인한다.

## 5. 세이브 호환 회귀 시험

- 기준 매핑으로 EBOOT를 생성하고 모든 기존 매핑의 글리프 비트맵 해시를 기록한다.
- 번역 입력 순서를 뒤집거나 섞어 다시 빌드해 기존 매핑이 바이트 단위로 동일한지 확인한다.
- 가상의 새 한글 한 글자를 추가한 격리 입력으로 빌드해 다음을 확인한다.
  - 기존 모든 문자 코드·인덱스 불변
  - 기존 글리프 비트맵 불변
  - 새 문자 한 건만 새 안전 슬롯에 추가
- 새 문자를 제거한 입력으로 다시 빌드해 기존 canonical 매핑이 축소되거나 재배정되지 않는지 확인한다.
- 102번 EBOOT와 기준 매핑에 포함된 글리프의 코드·비트맵을 비교한다.

## 6. GUI 동작

- 번역 저장 또는 사전 검증 시 신규 미등록 한글 수와 문자를 표시한다.
- 신규 문자가 없으면 기존 canonical mapping을 그대로 사용한다.
- 신규 문자가 있으면 안전한 추가 후보를 보고하고 명시적인 매핑 갱신 절차를 제공한다.
- GUI의 일반 ISO 빌드는 임시 재배정을 수행하지 않는다.
- 원버튼 갱신을 제공할 경우 기존 매핑 불변 검증을 통과한 뒤 canonical 파일을 append-only로 갱신한다.

- 검증 자료: `tools/patchdata/work/current/108-stable-hangul-mapping`
- 결과 문서: `docs/result/108-ys6-stable-hangul-glyph-mapping.md`

## 안전 조건

- 102번 또는 사용자가 실제 사용한 기준 패치와 매핑 관계가 확인되기 전에는 canonical 매핑을 확정하지 않는다.
- 기존 seed 192개는 모두 보존한다.
- 매핑 충돌을 자동 수정하지 않고 오류로 중단한다.
- 세이브 파일 자체는 수정하지 않는다.
- 원본 및 패치 ISO는 읽기 전용 비교 대상으로만 사용하며 이 단계에서 새 ROM은 만들지 않는다.

## 완료 기준

- 기존 약 978개 문자 매핑이 하나의 canonical 파일에 고정된다.
- 번역 순서 변경과 신규 문자 추가·제거에도 기존 코드·인덱스가 변하지 않는다.
- 미등록 문자는 임시 재배정되지 않고 append-only 절차로만 추가된다.
- 사전 검증과 manifest에서 매핑 revision 및 SHA-256을 확인할 수 있다.
- 102번 기준 EBOOT와 기존 글리프 호환성이 검증돼 기존 세이브의 저장 한글이 유지된다.
