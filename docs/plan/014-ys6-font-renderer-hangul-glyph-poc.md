# Ys VI 폰트·문자 렌더러 분석 및 한글 단일 글리프 PoC 계획

## 상태

- 계획 작성: 완료
- 사용자 확인: 대기
- 폰트·렌더러 분석: 완료
- 한글 단일 글리프 PoC: 1차 인게임 실패, EBOOT 적용 경로 재확인 필요

## 배경

다음 대사 처리 경로는 PPSSPP 인게임까지 검증됐다.

```text
XSR 문자열 교체
→ `.z` 재압축
→ `data/arc/s_0551.bin` 내장 엔트리 교체
→ ISO 삽입
→ 게임 표시
```

현재 XSR 문자열은 CP932이며 한글을 직접 인코딩할 수 없다. 실제 한글 패치를 진행하려면 게임이 PSP 시스템 PGF를 사용하는지, 게임 내장 폰트·텍스처를 사용하는지, 문자 코드가 글리프 번호로 어떻게 변환되는지 먼저 확인해야 한다.

## 목적

1. 대사 렌더링에 사용되는 폰트 자산과 코드 경로를 식별한다.
2. CP932 바이트열이 글리프 선택과 폭 계산으로 이어지는 방식을 확인한다.
3. 안전한 기존 문자 코드 하나를 시험용으로 선택해 글리프를 `한`으로 교체한다.
4. 시작 대사에서 한글 글리프 하나가 PPSSPP에 정상 표시되는지 검증한다.

이번 단계의 성공 기준은 완성형 한글 전체 지원이 아니라 한글 글리프 한 개의 인게임 출력이다.

## 원본 보호 및 작업본

- 원본 ISO `/roms/Ys VI - Napishtim no Hako (Japan).iso`는 읽기 전용으로 유지한다.
- 분석·추출 자료는 `/.work/ys6-font-renderer-poc`에 둔다.
- 수정 ISO가 필요하면 `/patched/014-hangul-glyph-poc`에 작업본 하나만 생성한다.
- 기존 `/patched/009-talkkebin-string-poc/Ys VI - first-dialogue-poc.iso`는 보존하고 변경하지 않는다.
- 원본 게임 데이터와 수정 ISO는 Git에 포함하지 않는다.
- PoC 종료 후 불필요해진 작업 ISO와 대용량 추출물은 결과 문서에 정리 대상으로 기록한다.

## 1단계: 폰트 자산 조사

ISO 전체 파일 목록에서 다음 후보를 조사한다.

- `.pgf`, `.bwfon`, `.fnt`, `.font` 등 알려진 폰트 확장자와 매직
- GIM, DDS 및 독자 텍스처 중 문자 격자 형태의 이미지
- 문자 폭, UV 좌표 또는 글리프 인덱스로 보이는 고정 크기 테이블
- `data/arc/*.bin` 안에만 존재하는 내장 자산
- `BOOT.BIN` 및 PRX의 폰트 관련 경로·문자열

확장자만으로 판단하지 않고 매직, 크기, 엔트로피와 시각적 격자 특성을 함께 기록한다.

필요한 비GUI 조사 도구는 `/tools/scripts`에 Python으로 작성한다.

## 2단계: 렌더러 경로 판별

평문 ELF인 `PSP_GAME/SYSDIR/BOOT.BIN`을 우선 분석한다.

- PSP `sceFont*` import 또는 PGF 관련 호출 여부
- CP932 선행 바이트·후행 바이트 판정 코드 후보
- 문자열 폭 계산, 줄바꿈, 글리프 조회 및 텍스처 전송 후보
- XSR 대사 opcode 처리와 렌더러 호출 사이의 연결

PPSSPP 디버거가 필요하면 localhost 전용으로만 활성화하고, 작업 전 설정을 백업하며 종료 후 원래대로 복원한다. 대사 출력 시점의 원문 버퍼, 디코딩 결과 및 글리프 데이터 접근을 정적 분석과 교차 검증한다.

`EBOOT.BIN` 복호화가 필요하다고 판단되면 즉시 진행하지 않는다. 필요성, 도구, 산출물 및 위험을 계획 문서에 추가하고 사용자에게 다시 확인받는다.

## 3단계: 시험 코드포인트 선정

전체 대사 카탈로그와 시스템 문자열에서 CP932 문자 사용 빈도를 계산한다.

선정 조건:

- 시작 장면과 일반 플레이에서 사용되지 않거나 사용 빈도가 극히 낮음
- CP932에서 안정적으로 2바이트 인코딩 가능
- 제어 토큰, 경로, 심볼 및 루비 마크업에 사용되지 않음
- 폰트 테이블의 기존 글리프 위치를 명확히 찾을 수 있음

시험 문자는 실제 한글 코드로 저장하지 않는다. 선정한 CP932 자리의 글리프 이미지만 `한`으로 교체하여 기존 문자열 파서와 XSR 형식을 유지한다.

선정한 문자와 충돌 위험은 결과 문서에 기록한다.

## 4단계: 한글 단일 글리프 제작

렌더러 판별 결과에 따라 한 가지 방식만 선택한다.

### 게임 내장 비트맵·텍스처 폰트인 경우

- 원본 글리프 크기, 베이스라인, 여백, 색 깊이와 알파 형식을 유지한다.
- 선정한 한 글리프 셀만 `한`으로 교체한다.
- 다른 글리프와 메타데이터는 변경하지 않는다.

### PSP PGF 또는 독자 벡터 폰트인 경우

- 기존 포맷의 글리프 단위 교체 가능성을 먼저 검증한다.
- 안전한 재구성이 불가능하면 실행 파일 패치나 새 폰트 주입을 임의로 진행하지 않고 별도 계획으로 분리한다.

글리프 원본은 재배포 가능한 폰트 또는 직접 제작한 시험용 비트맵을 사용한다. 외부 폰트 의존성이 필요하면 라이선스와 설치 필요성을 문서화하고 진행 전에 확인받는다.

## 5단계: 시작 대사 PoC

인게임 위치가 확정된 `s_0551` 시작 대사를 사용한다.

- 런타임 대상: `PSP_GAME/USRDIR/data/arc/s_0551.bin`
- 내장 파일: `s_0551.xso.z`
- 문자열 인덱스: 35
- 대사에 선정한 시험 CP932 문자를 한 번 삽입
- 해당 문자 위치가 화면에서 `한`으로 표시되는지 확인

문자열은 가능한 한 원문과 같은 CP932 바이트 길이를 유지한다. 길이 변경이 필요하면 이번 단계에서 강행하지 않고 XSR 가변 길이 재구성 계획으로 분리한다.

## 6단계: 패치 및 검증

- 폰트 자산과 내장 XSO를 각각 준비하고 구조를 재검증한다.
- 관련 통합 아카이브가 있으면 기존 `ys6_arc.py`를 사용해 내부 엔트리를 교체한다.
- 원본 ISO에서 `/patched/014-hangul-glyph-poc` 작업 ISO 하나를 생성한다.
- ISO 전체 diff를 검사하여 승인된 폰트·대사 자산 범위 밖 변경이 없음을 확인한다.
- 작업 ISO에서 모든 수정 자산을 재추출해 준비 파일과 SHA-256을 비교한다.
- PPSSPP 새 게임에서 시작 대사의 시험 글리프를 확인한다.

## 구현 예정 위치

분석 결과에 따라 필요한 최소 도구만 추가한다.

- 폰트·글리프 조사 스크립트: `/tools/scripts`
- 폰트 이미지 확인이 필요한 사용자용 GUI가 필요해질 경우: `/tools`

## 검증 기준

- 실제 대사 렌더러가 사용하는 폰트 출처가 증거와 함께 확인된다.
- 문자 코드에서 글리프 선택까지의 경로가 최소 PoC에 필요한 수준으로 설명된다.
- 선정한 시험 CP932 문자의 전체 사용처와 충돌 위험이 기록된다.
- 원본 폰트와 수정 폰트의 차이가 대상 글리프에 한정된다.
- 수정 XSO가 구조·CP932·압축 검사를 통과한다.
- 수정 아카이브와 ISO에서 허용 범위 밖 변경이 없다.
- 원본 ISO SHA-256이 유지된다.
- 관련 단위 테스트와 Python 바이트코드 컴파일이 통과한다.
- PPSSPP에서 `한` 글리프 한 개가 정상 표시되거나, 실패 원인이 폰트·매핑·렌더러 단계 중 하나로 특정된다.

## 진행 중 분석 기록

### 정적 자산 조사

- ISO 파일명과 `data/arc/*.bin` 내부 엔트리 이름에서 전용 폰트 파일은 발견되지 않았다.
- ISO에 `PSP_GAME/USRDIR/module/libfont.prx`와 `libccc.prx`가 존재하지만, 평문 `BOOT.BIN`에는 `sceFont*` import와 해당 PRX 로드 경로가 없다.
- `.z` 압축 해제 대상과 전체 ISO 자산을 알려진 폰트 매직으로 검사했으나 PGF 계열 시작 매직은 발견되지 않았다.
- 조사 스크립트는 `tools/scripts/ys6_font_scan.py`에 작성했고 결과는 `.work/ys6-font-renderer-poc/font-scan.json`에 보관한다.

### PPSSPP 런타임 조사

- 첫 대사 표시 시 실행 중인 게임 모듈은 `ys6psp` 하나로 확인됐다.
- 실행 함수 목록에 `sceFont*` 계열 import가 없으므로 시스템 PGF 렌더러를 사용하는 경로는 배제한다.
- 테스트 대사의 CP932 바이트열은 다음 두 주소에서 확인됐다.
  - `0x09529C72`: 로드된 XSR 문자열 풀
  - `0x08D0A8C0`: 화면 출력용 대사 버퍼
- CP932 바이트열은 렌더링 직전까지 변환되지 않은 채 유지되므로 게임 코드가 CP932 값을 자체 글리프 번호로 대응시키는 것으로 판단한다.
- 대사 시점 VRAM 2 MiB를 `.work/ys6-font-renderer-poc/vram-first-dialogue.bin`으로 확보했다.
- PSP 주요 픽셀 형식으로 렌더링한 결과 VRAM에는 완성된 화면 프레임버퍼 두 벌만 보이고 별도 글리프 아틀라스는 확인되지 않았다.
- 이 결과는 CPU 측에서 글리프를 프레임버퍼에 합성하는 구조와 일치한다. 다음 추적에서는 대사 영역 픽셀 쓰기 지점에 메모리 중단점을 걸어 렌더러 함수와 글리프 원본 주소를 역추적한다.

### 추가된 진단 도구

- `tools/scripts/nodejs/ys6_ppsspp_memory_dump.js`: PPSSPP 원격 디버거 메모리 구간 덤프
- `tools/scripts/ys6_vram_render.py`: PSP VRAM의 RGB565·RGBA5551·RGBA4444·8비트 시각화
- `tools/scripts/ys6_font_table.py`: `BOOT.BIN` 내장 16×12 글리프 테이블 추출
- `tools/scripts/ys6_font_patch.py`: TTC/TrueType 글꼴에서 단일 글리프를 렌더링해 기존 글리프 비트맵 교체

### 단일 한글 글리프 PoC 구현

- 내장 폰트 테이블은 `BOOT.BIN` 파일 오프셋 `0x13E88C`에 있다.
- 레코드는 4,608개이며 각 레코드는 CP932 코드 2바이트와 16×12 1bpp 비트맵 24바이트로 구성된다.
- 전체 추출 문자열에서 사용되지 않는 `0x98FC`(`傲`, 인덱스 4605)를 시험 코드로 선택했다.
- `C:/Windows/Fonts/gulim.ttc`의 Gulim Regular, 12px를 사용해 `한`을 16×12 1bpp로 렌더링했다.
- 원본 TTC 파일은 복사하거나 결과물에 포함하지 않고 생성된 24바이트 비트맵만 `BOOT.BIN`에 반영했다.
- 시작 대사는 `0x98FC` 1글자와 전각 공백 10개로 교체해 기존 22바이트 길이를 유지했다.
- PoC ISO: `/patched/014-hangul-glyph-poc/Ys VI - hangul-glyph-poc.iso`
- 최종 ISO SHA-256: `E8FB55D2D2B76427A97CC977662CF29C54CDD3E8BE9E36F588B2FFAED345711B`
- 전체 단위 테스트 38개가 통과했고 허용 범위 밖 ISO 변경은 0건이다.
- 1차 인게임 검증에서 `한`이 아니라 교체 전 문자 `傲` 글리프가 표시됐다.
- 대사 코드 `0x98FC`는 정상 적용됐으므로 `s_0551.bin` 패치는 실행 중 사용되고 있다.
- 반면 `BOOT.BIN`에 교체한 비트맵은 실행 중 사용되지 않았다. PPSSPP가 실제 실행 이미지로 `EBOOT.BIN`을 사용하고 `BOOT.BIN` 변경은 부팅에 반영하지 않는 것이 가장 유력한 원인이다.
- 이는 이 계획의 중단 조건인 `EBOOT.BIN` 복호화 또는 수정 필요에 해당한다. EBOOT 적용 경로를 별도 단계로 계획하고 사용자 확인을 받기 전에는 추가 실행 파일 패치를 진행하지 않는다.
