# 039. 전체 draft 제어문자·루비·특수문자 정규화 계획

## 목적

계획 038에서 발견된 전체 draft 적용 blocker 중 사용자가 승인한 1~4번 범위를 처리한다.

1. 플레이어명 변수 `\x1`이 `아돌`로 고정된 번역을 의도된 변경으로 허용한다.
2. 잘못 남은 단독 백슬래시를 정상 줄바꿈 `\n`으로 고친다.
3. 일본어 독음용 루비 태그를 한국어 번역에서 제거한 상태로 승인한다.
4. PSP 코덱이 지원하지 않는 특수문자를 지원되는 유사 문자로 정규화한다.

공유 payload 충돌, many-to-many 런타임 대응, 비정확 대응 검수 및 전체 일괄 승인은 이번 작업에서 보류한다.

## 1. 플레이어명 `아돌` 고정 허용

### 방침

- Windows판 번역에서 `\x1` 대신 `아돌`로 풀어 쓴 258개는 그대로 유지한다.
- 번역문을 다시 `\x1`로 바꾸지 않는다.
- 현재 검증기는 원문과 번역문의 모든 제어 토큰이 같아야 하므로, 레코드 단위로 플레이어명 변수 확장을 명시적으로 허용하는 메타데이터를 추가한다.

예상 메타데이터:

```json
"allow_player_name_expansion": true
```

### 검증기 변경

- `allow_player_name_expansion`이 참인 경우에만 원문의 `\x1`과 번역문의 고정 `아돌` 차이를 허용한다.
- `\n`, `\x3`, `\x4` 등 다른 제어 토큰 불일치는 계속 오류로 처리한다.
- 허용 필드가 없는 기존 레코드의 검증 규칙은 바꾸지 않는다.
- 동기화 및 CSV 작업에서 해당 필드가 유실되지 않게 한다.

## 2. 단독 백슬래시 줄바꿈 정규화

계획 038에서 정상 토큰이 아닌 단독 `\`가 있는 번역 15개를 확인했다.

### 처리 기준

- 원문에서 같은 문맥 위치에 `\n`이 있고 번역문에서 줄 경계가 단독 `\`로 남은 경우 `\n`으로 바꾼다.
- `\n`, `\x1`, `\x3`, `\x4`, `\s` 등 정상 토큰은 건드리지 않는다.
- 기계적으로 확정하기 어려운 항목은 변경하지 않고 검토 목록으로 남긴다.
- 변경 전후 문장과 근거를 비교 보고서에 기록한다.

예:

- `정령들에의\감사의 마음을` → `정령들에의\n감사의 마음을`
- `그걸\오르하에게 넘겨주게.` → `그걸\n오르하에게 넘겨주게.`

## 3. 일본어 독음용 루비 제거 승인

### 판정 기준

원문에서 다음 쌍으로 쓰인 루비만 일본어 독음용으로 판정한다.

- `<ruby:오프셋,길이>독음<endruby>`

한국어 번역에서 루비 태그와 일본어 독음이 제거되고 본문 의미가 남아 있으면 레코드에 다음을 설정한다.

```json
"allow_markup_change": true
```

### 다른 마크업 처리

- `<color:...>`, `<color:>`, `<scale:...>`는 루비가 아니므로 자동 제거를 허용하지 않는다.
- 원문과 번역의 색상·크기 태그가 달라진 항목은 별도 검토 대상으로 남긴다.
- 루비와 색상 태그가 함께 있는 문장은 색상 태그가 유지된 경우에만 자동 승인한다.
- 루비 제거 외의 마크업 차이가 함께 있으면 `allow_markup_change`를 자동 설정하지 않는다.

### 예상 분석

- 루비 제거 후보 136개의 태그 차이를 다시 분해한다.
- 순수 루비 제거인지, 색상·크기 태그 차이까지 포함하는지 집계한다.
- 자동 승인 수와 보류 수를 기록한다.

## 4. 미지원 특수문자 정규화

현재 미지원 문자와 제안 치환은 다음과 같다.

| 미지원 문자 | 제안 치환 | 이유 |
|---|---|---|
| `─` | `-` | ASCII 하이픈은 이미 지원되며 긴 대시 의미를 유지할 수 있음 |
| `～` | `~` | ASCII 물결표가 이미 지원됨 |
| `《` | `<` | 쌍으로 쓰는 강조 괄호 의미를 유지하고 ASCII 지원됨 |
| `》` | `>` | 위와 동일 |
| `①` | `(1)` | 숫자 의미를 확실하게 보존하며 모두 지원됨 |
| `②` | `(2)` | 위와 동일 |
| `③` | `(3)` | 위와 동일 |
| `ㆍ` | `·` 우선, 미지원이면 `.` | 가운데점 의미를 최대한 유지 |
| `★` | `*` | 장식·강조 의미를 유사하게 유지하고 ASCII 지원됨 |

### 확정 전 검사

- `·`가 기존 PSP CP932 코드로 인코딩 가능한지 먼저 시험한다.
- `<`와 `>`가 게임의 마크업 파서에서 일반 본문 문자로 안전한지 검사한다. 마크업으로 오인될 가능성이 있으면 `[`와 `]` 또는 일본어 괄호 `「`와 `」` 중 기존 지원 문자를 사용한다.
- 치환 후 모든 대상 문장이 `encode_translation`을 통과하는지 확인한다.
- 치환 전후 문장을 비교 보고서에 남긴다.

## 구현 범위

### 스크립트

`/tools/scripts`에 비GUI 정규화 스크립트를 추가하거나 기존 작업공간 스크립트를 확장한다.

기능:

- 플레이어명 확장 후보 탐지 및 메타데이터 설정
- 단독 백슬래시 탐지·안전 교정
- 순수 일본어 루비 제거 후보 판정 및 허용 설정
- 특수문자 안전성 시험과 확정 치환
- 미리보기, 적용, 비교 보고서 분리
- 적용 전 전체 작업공간 백업

예상 파일:

- `/tools/scripts/ys6_draft_normalize.py`

### 검증기

- `/tools/scripts/ys6_translation_workspace.py`
- 플레이어명 고정 허용 필드 보존 및 제한적 검증
- 기존 제어 토큰 보호 규칙 유지

## 적용 절차

1. 현재 번역 작업공간 SHA-256과 상태별 수량을 기록한다.
2. `.work/ys6-draft-normalization`에 전체 백업을 만든다.
3. 미리보기 복사본에서 네 종류의 정규화를 수행한다.
4. 변경 전후 비교 JSON과 보류 목록을 생성한다.
5. 미리보기 작업공간 검증을 실행한다.
6. 사용자 승인 범위와 규칙에 맞는 변경만 실제 작업공간에 적용한다.
7. 적용 후 작업공간 검증을 다시 실행한다.
8. 전체 draft를 가상 override로 승격해 제어 토큰·마크업·미지원 문자 blocker가 해소됐는지 확인한다.
9. 결과 문서를 작성한다.

## 검증 기준

- `아돌` 고정 258개가 번역문 변경 없이 검증 가능해야 한다.
- 다른 제어 코드 불일치는 여전히 오류로 검출되어야 한다.
- 단독 백슬래시가 안전 교정 대상에서 0개가 되어야 한다.
- 순수 루비 제거만 자동 허용되고 색상·크기 차이는 보류되어야 한다.
- 정규화한 특수문자가 모두 PSP 인코더를 통과해야 한다.
- 작업공간 레코드 수와 `draft` 상태는 유지한다.
- 실제 ISO를 만들거나 수정하지 않는다.
