## 1차 인게임 확인

- 수정 ISO 단독 부팅 및 첫 대사 출력에 성공했다.
- 기존 대체 문자 `傲`가 아니라 한글 기반 비트맵이 출력되므로, 복호화 EBOOT의 폰트 패치가 실제 런타임에 적용됨을 확인했다.
- 다만 16×12 셀에 자동 축소된 `gulim.ttc`의 `한` 비트맵이 화면에서는 `힌`처럼 보인다.
- 이는 코드 매핑이나 EBOOT 적용 실패가 아니라 작은 셀에서의 래스터라이징 및 획 배치 문제로 판정한다.
- 추가 화면 확인 결과, 핵심 원인은 획 두께가 아니라 렌더러의 실제 가시 폭에서 오른쪽 `ㅏ` 가로획이 잘리는 좌표 문제로 정정한다.
- 후속 보정은 글리프 구성 요소를 왼쪽 안전 영역으로 이동하며 획 두께는 늘리지 않는다.

## 배경

계획 014에서 다음 사항을 확인했다.

- 게임은 PSP 시스템 폰트가 아니라 실행 파일에 내장된 16×12 1bpp 글리프 테이블을 사용한다.
- CP932 코드→글리프 인덱스 함수는 `0x0882CB94`, 글리프 렌더링 함수는 `0x0882CFFC`다.
- 평문 `BOOT.BIN`의 파일 오프셋 `0x0013E88C`에 4,608개의 26바이트 글리프 레코드가 있다.
- `0x98FC`(`傲`, 인덱스 4605)는 전체 추출 문자열 7,424개에서 사용되지 않았다.
- `gulim.ttc`로 만든 `한` 비트맵을 `BOOT.BIN`에 넣었지만 인게임에서는 원래 `傲` 글리프가 표시됐다.
- 대사 코드 `0x98FC`는 정상 반영됐으므로 대사 아카이브 패치는 성공했고, 실패 원인은 수정 `BOOT.BIN`이 실제 부팅 이미지로 사용되지 않은 데 있다.

PPSSPP가 실제로 사용하는 `EBOOT.BIN`의 복호화 이미지를 분석하고 수정한 실행 파일을 ISO 내부에 포함해, 외부 파일 없이 ISO 하나만으로 한글 글리프가 표시되는지 검증한다.

## 목표

1. PPSSPP에서 Ys VI의 복호화 실행 이미지를 안전하게 덤프한다.
2. 덤프본과 평문 `BOOT.BIN`의 코드·폰트 테이블 대응 관계를 확인한다.
3. 덤프된 실행 파일의 `0x98FC` 글리프를 `gulim.ttc` 기반 `한` 비트맵으로 교체한다.
4. 수정 실행 파일을 ISO의 `PSP_GAME/SYSDIR/EBOOT.BIN`에 삽입한다.
5. 별도 치트, 플러그인, 텍스처팩 또는 외부 파일 없이 수정 ISO 하나로 PPSSPP에서 부팅한다.
6. 새 게임 첫 대사에서 `한` 글리프가 표시되는지 확인한다.

## 1단계: PPSSPP 덤프 방법 확인

PPSSPP 개발자 도구의 `Dump decrypted EBOOT.BIN on game boot` 기능을 사용한다.

- 현재 PPSSPP 설정 파일을 작업 폴더에 백업한다.
- 복호화 EBOOT 덤프 옵션만 일시적으로 활성화한다.
- 계획 014에서 인게임 실행이 확인된 ISO로 게임을 부팅한다.
- 생성된 덤프 파일의 정확한 경로, 크기 및 SHA-256을 기록한다.
- 덤프 완료 후 PPSSPP를 종료하고 설정을 원래 값으로 복구한다.

진단 설정은 localhost와 로컬 파일 범위에서만 사용하며 ISO에는 이 단계에서 변경을 가하지 않는다.

## 2단계: 덤프 실행 파일 구조 검증

덤프본이 다음 조건을 만족하는지 확인한다.

- ELF 또는 PSP가 직접 실행 가능한 평문 실행 이미지인지 확인
- 프로그램 세그먼트, 로드 주소 및 진입점 확인
- 실행 코드가 기존 `BOOT.BIN`과 동일하거나 대응 가능한지 비교
- 런타임에서 확인한 함수 주소 `0x0882CB94`, `0x0882CFFC`의 명령열 비교
- CP932 선행 바이트 판정표 및 폰트 테이블 탐색
- `0x98FC` 레코드가 원래 `傲` 비트맵인지 시각·바이트 단위 검증

고정 파일 오프셋을 가정하지 않고 ELF 세그먼트의 파일 오프셋과 가상 주소 관계로 폰트 위치를 다시 계산한다.

## 3단계: 수정 EBOOT 생성

계획 014에서 만든 도구를 우선 재사용한다.

- `/tools/scripts/ys6_font_table.py`
- `/tools/scripts/ys6_font_patch.py`

필요하면 덤프 ELF의 재배치 기준을 자동 계산하도록 도구를 보완한다.

글리프 적용 조건:

- 대상 코드: `0x98FC`
- 대상 인덱스: 덤프본 테이블에서 다시 확인
- 대상 문자: `한`
- 원본 글꼴: `C:/Windows/Fonts/gulim.ttc`
- 글꼴 면: Gulim Regular, TTC 인덱스 0
- 렌더링 크기: 12px
- 결과 형식: 16×12px, 1bpp, 24바이트
- 코드값, 레코드 수, 테이블 크기 및 실행 코드는 변경하지 않음

수정 전후 차이가 대상 글리프 비트맵 24바이트 범위 안에만 있는지 확인한다.

## 4단계: EBOOT 교체 가능성 확인

ISO의 기존 `PSP_GAME/SYSDIR/EBOOT.BIN`에 대해 다음을 확인한다.

- 현재 파일 크기와 할당 섹터
- 수정 EBOOT 크기
- 기존 할당 공간 내 교체 가능 여부
- ISO 9660 디렉터리 크기 필드 변경 필요 여부
- PPSSPP가 평문 ELF를 `EBOOT.BIN` 경로에서 직접 실행할 수 있는지

수정 EBOOT가 기존 할당 공간보다 크면 즉시 ISO를 확장하거나 파일을 재배치하지 않는다. 필요한 크기, 재배치 범위와 위험을 계획에 추가하고 사용자에게 다시 확인받는다.

## 5단계: 대사 PoC 아카이브 준비

계획 014에서 검증한 대사 패치를 재사용한다.

- 내장 파일: `s_0551.xso.z`
- 문자열 인덱스: 35
- 시험 코드: `0x98FC`
- 시험 문자열: `0x98FC` 1글자와 전각 공백 10개
- 문자열 길이: 기존과 동일한 22바이트

XSO 구조, `.z` CRC32, 압축 해제 크기, 아카이브 할당 범위를 다시 검증한다.

## 6단계: 단일 PoC ISO 생성

원본 또는 검증된 기준 ISO에서 `/patched/015-decrypted-eboot-hangul-poc`의 작업 ISO 한 개를 만든다.

1. `PSP_GAME/SYSDIR/EBOOT.BIN`
2. `PSP_GAME/USRDIR/data/arc/s_0551.bin`

생성 후 다음을 검증한다.

- 두 내부 파일의 재추출 SHA-256
- 수정 EBOOT의 글리프 레코드 재검사
- 수정 아카이브의 문자열·압축·할당 범위 재검사
- 기준 ISO와의 전체 바이트 diff
- 허용 범위 밖 변경 0건

## 7단계: PPSSPP ISO 단독 검증

외부 덤프 파일이 없어도 작동하는지 확인하기 위해 다음 조건으로 시험한다.
