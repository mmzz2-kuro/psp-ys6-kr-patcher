### `s_0202/OruhaMove` 인게임 실패 재분석 및 범위 변경안 (2026-08-12)

사용자가 실제 `s_0202/OruhaMove` 선택지에서 일본어 출력을 확인했다. 이에 023 ISO를 다시 정적으로 검사한 결과, 앞선 판단을 정정한다.

- 아카이브 사본 `data/arc/s_0202.bin#19:OruhaMove.xso.z`
  - 컨테이너: 1,132바이트
  - 컨테이너 SHA-256: `BFA5DFAE55D26056AE5C95DBB37628BE3724E1E11FF6DBDD962EF9AE610A5E06`
  - 한글 payload SHA-256: `3A8375783A346B66B51EB46EF4A4E7573175090A18BA2AF514D51A89C127C11E`
  - 빌드 준비본과 바이트 단위 일치
- standalone 사본 `data/map/s_02/s_0202/oruhamove.xso.z`
  - 컨테이너: 1,119바이트
  - 컨테이너 SHA-256: `B164A557316908019E35271FC656C81B945698516152EE8A09CBA644CED5394B`
  - 일본어 payload SHA-256: `20234A07B4549F42E6975F2DCC01F4F08C919778CF9DE23FED1295974BD17974`
  - 023에서 변경되지 않음
- 인게임 결과와 결합하면 이 이벤트는 아카이브 사본이 아니라 standalone 사본을 직접 읽는 것으로 판정한다.
- standalone ISO 레코드: LBA 159,568, 원본 길이 1,119바이트, 할당 2,048바이트, 원본 잔여 929바이트
- 한글 컨테이너 1,132바이트는 기존 할당보다 916바이트 작으므로 extent 이동이나 파일 재배치 없이 교체 가능하다.

승인 후 추가 구현 범위:

1. 통합 빌더가 동일 원본 payload의 확정된 standalone 경로를 명시적으로 추가 교체할 수 있게 한다.
2. `s_0202/OruhaMove`의 아카이브 사본과 standalone 사본에 동일한 한글 컨테이너를 적용한다.
3. ISO 디렉터리 레코드의 파일 길이를 1,132바이트로 안전하게 갱신한다.
4. LBA와 전체 ISO 크기를 유지하고, 허용된 standalone extent 및 길이 필드 밖 변경 0건을 검증한다.
5. 기존 023 ISO를 덮어쓰지 않고 새 검증 ISO를 생성한 뒤 인게임에서는 `s_0202/OruhaMove`만 재확인한다.

이 변경은 최초 계획에서 제외한 standalone 직접 로드를 포함하므로 사용자 확인 전에는 구현하지 않는다.

## 배경

계획 020은 `/data/arc`의 flags `0x01000000` 엔트리만 파일 데이터로 취급해 런타임 XSO 344개를 대응했다. 계획 022의 정적·PPSSPP 조사에서 아카이브에는 flags `0x41000000`인 보조 데이터 엔트리가 별도로 존재하며, 이 중 XSO가 71개임을 확인했다.

`AdolSleep.xso.z`는 다음 위치에 정확히 존재하고 실제 이벤트 전후 PPSSPP 메모리에서 압축본·비압축 XSO 전체가 확인됐다.

- 아카이브: `PSP_GAME/USRDIR/data/arc/s_020a.bin`
- 엔트리: 16 `AdolSleep.xso.z`
- flags: `0x41000000`
- 오프셋: `0x1D800`
- 크기: 1,534바이트
- 다음 데이터 경계까지 할당: 2,048바이트
- 원본 여유: 514바이트

따라서 `0x41000000`은 무시 가능한 패딩이 아니라 로더가 사용하는 보조 엔트리다. `OruhaMove.xso.z`도 동일 유형으로 `s_0202.bin`에 정확히 대응한다. 이 유형을 020 대응 정본과 021 통합 빌더에 안전하게 포함해야 한다.

## 목표

1. 아카이브 파서가 일반 엔트리와 보조 데이터 엔트리를 명시적으로 구분한다.
2. 데이터가 있는 모든 엔트리의 할당 경계를 정확히 계산한다.
3. 020 대응 분석에 보조 XSO 71개를 포함한다.
4. 기존 대응 결과와 새 보조 대응 결과를 새 스키마에서 재현한다.
5. 021 통합 빌더가 확정된 `0x41000000` XSO를 재조립·압축·교체한다.
6. 일반 XSO와 보조 XSO를 같은 아카이브 작업본에 함께 적용할 수 있게 한다.
7. `AdolSleep`과 `OruhaMove` 번역을 사전 빌드하고 할당 여부를 확인한다.
8. 안전 조건을 통과하면 기존 `s_0551` 번역과 함께 하나의 023 ISO를 생성한다.

## 범위

- flags `0x01000000`: 일반 데이터 엔트리
- flags `0x41000000`: 보조 데이터 엔트리
- 대상 확장: `/data/arc` 내부 XSO
- 번역 입력: 런타임 대응이 확정되고 사용자가 작성한 번역만 사용
- 기존 `s_0551` 29개 번역을 회귀 대상으로 유지
- `AdolSleep` 4개와 `OruhaMove` 9개를 신규 적용 후보로 사용

이번 단계에 포함하지 않는 항목:

- standalone 직접 로드 후보
- `s_hidden1`과 `s_9000`/`s_9002`의 구조 변형 자동 병합
- `talkkebin`, `talktokusa` 변형 번역 전파
- 아카이브 전체 재배치·확장
- 메뉴·이미지·실행 파일 문자열
- 사용자용 GUI 연결

- 원본 SHA-256 `0133DC75EEEFB7E1864180C88E486D2EEBE9AE3D1DBFA990BEF57E28BAAE082B`를 전후 확인한다.
- 021 최종 ISO는 덮어쓰지 않는다.
- 023 작업 경로는 `/.work/ys6-auxiliary-xso-support`로 분리한다.
- 최종 ISO는 `/patched/023-auxiliary-xso-support`에 한 개만 둔다.
- 번역 정본은 수정하지 않고 별도 검수 입력을 생성한다.
- PPSSPP 설정은 현재 원복 상태를 유지한다. 번역 적용 인게임 검증에 메모리 추적은 기본적으로 사용하지 않는다.

## 1단계: 아카이브 flags 모델 확장

`ys6_arc.py`에 다음 상수를 명시한다.

- `FILE_FLAG = 0x01000000`
- `AUXILIARY_FILE_FLAG = 0x41000000`
- 데이터 엔트리 flags 집합

`ArcEntry`에는 엔트리 종류를 판별할 수 있는 정보를 제공한다.

- 일반 데이터
- 보조 데이터
- 디렉터리·그룹
- 기타

기존 `find_file()`은 하위 호환을 위해 일반 데이터만 찾는 동작을 유지하거나, 허용 flags를 명시적으로 받게 한다. 통합 빌더는 정확한 index·name·flags를 모두 검증해 대상 엔트리를 선택한다.

## 2단계: 할당 경계 계산 수정

기존 파서는 `0x01000000` 엔트리의 오프셋만 사용해 할당 크기를 계산하므로, 그 사이에 위치한 `0x41000000` 데이터를 일반 파일의 패딩처럼 포함한다.

새 계산은 다음을 따른다.

- 크기와 오프셋이 있는 모든 데이터 엔트리를 오프셋 순으로 정렬
- 다음 데이터 엔트리 시작 또는 아카이브 끝을 현재 엔트리의 할당 경계로 사용
- 중복·역행·중첩 오프셋 차단
- 실제 크기가 할당을 넘으면 오류
- 0x800 정렬 여부 기록 및 기존 포맷 규칙 검증

이 변경으로 일반 엔트리의 기존 `allocated_size`가 줄어들 수 있다. 이는 이전 값이 보조 데이터를 패딩으로 잘못 포함했던 것이므로, 모든 기존 교체 도구와 테스트에서 회귀 검증한다.

## 3단계: 안전 교체 API 확장

아카이브 교체 함수는 다음을 지원한다.

- 일반 또는 보조 데이터 엔트리 교체
- 엔트리 index·name·flags 일치 검증
- 기존 할당 내 크기 변경
- size 필드만 갱신
- 다음 엔트리와 대상 외 데이터 보존
- 교체 후 전체 아카이브 재파싱

보조 엔트리를 일반 엔트리의 이름 검색으로 우연히 선택하지 않도록 한다. 동일 이름이 여러 flags에 있으면 index와 flags 없이는 중단한다.

## 4단계: 020 대응표 스키마 확장

`ys6_runtime_archive_map.py`가 `0x01000000`과 `0x41000000` XSO를 모두 수집하도록 변경한다.

런타임 키에는 기존 형식을 유지하되 각 엔트리에 다음 필드를 추가한다.

- `entry_flags_hex`
- `entry_kind`
- `entry_index`
- `allocated_size`
- `slack_size`

새 대응표는 `/.work/ys6-runtime-archive-map-v2`에 생성해 기존 020 산출물을 덮어쓰지 않는다. 스키마 버전을 올리고 020 v1과 혼용되지 않게 한다.

검증 항목:

- 기존 일반 XSO 344개가 유실되지 않음
- 보조 XSO 71개가 추가됨
- 전체 런타임 XSO 예상 415개
- `AdolSleep`, `OruhaMove` 정확 대응
- 중복·미대응 상태 합계
- 모든 정상 엔트리의 압축·XSO 무결성

실제 분석 결과가 예상 415개와 다르면 오류가 아니라 원인을 조사하고 문서화한다.

## 5단계: 021 통합 빌더 대응

`ys6_integrated_build.py`가 v2 대응표의 엔트리 index·name·flags를 사용한다.

- 원본 아카이브에서 정확한 엔트리를 선택
- flags와 원본 컨테이너 SHA-256 검증
- 같은 아카이브 내 일반·보조 XSO를 함께 누적 적용
- 엔트리별 수정 압축 크기와 새 할당 크기 비교
- 하나라도 초과하면 전체 빌드 중단
- 대상 외 보조·일반 엔트리 원시 바이트 보존

v1 대응표를 입력하면 보조 엔트리 적용을 조용히 생략하지 않고 지원 범위를 명시적으로 보고한다.

## 6단계: 검수 번역 입력 준비

사용자 번역 정본에서 다음만 별도 검수 입력으로 복사한다.

- `s_0551`: 이미 검증한 29개
- `oruhamove`: 현재 번역된 9개
- `adolsleep`: 현재 번역된 4개

처리:

- 실제 줄바꿈을 게임 `\n` 토큰으로 변환
- 원문 토큰·마크업 개수 검증
- 원문 SHA-256과 문자열 인덱스 검증
- 빈 번역 제외
- 번역 정본 상태는 변경하지 않음

토큰이나 마크업 불일치는 자동으로 문장을 바꾸지 않고 사용자 확인을 받는다.

## 7단계: 사전 빌드

전체 번역 문자 집합으로 원본 EBOOT에서 글리프를 재생성하고 XSO 3개를 빌드한다.

각 XSO에 대해:

- 원본·수정 XSO 크기
- 압축 크기
- 할당 크기와 남은 공간
- 적용 문자열 수
- payload·컨테이너 SHA-256

판정:

- 세 XSO 모두 할당 이내: ISO 생성 진행
- 하나라도 초과: 전체 ISO 생성 중단

초과 시 아카이브 재배치를 임의로 구현하지 않는다.

## 8단계: ISO 생성 및 정적 검증

원본 ISO에서 다음만 교체한다.

1. 전체 글리프 EBOOT
2. `s_0551.bin`
3. `s_0202.bin`
4. `s_020a.bin`

검증:

- 각 아카이브 크기·extent 유지
- 수정 일반·보조 XSO 재추출 해시 일치
- 대상 외 아카이브 엔트리 보존
- 모든 번역 원시 바이트 역검증
- EBOOT 글리프·매핑 일치
- 허용 extent 밖 ISO 변경 0건
- 원본 ISO SHA-256 유지
- 실패 시 `.partial` ISO 삭제

## 9단계: 인게임 검증

- `s_0551` 기존 29개 회귀 확인
- `AdolSleep` 번역 4개 출력과 이벤트 진행 확인
- `OruhaMove` 번역 9개 출력과 이벤트 진행 확인
- PPSSPP 완전 종료 후 새 실행 또는 정상 세이브 로드
- 세이브 스테이트를 사용한 경우 캐시·로드 시점 영향을 별도로 기록

이번에는 로드 경로가 이미 확정됐으므로 메모리 추적과 진단 설정 변경을 반복하지 않는다. 번역이 나오지 않을 때만 정적 검증을 재확인한 뒤 별도 진단 여부를 논의한다.

## 완료 조건

- flags `0x41000000`이 명시적인 보조 데이터 엔트리로 파싱된다.
- 모든 데이터 엔트리의 할당 경계가 다음 실제 데이터 오프셋 기준으로 계산된다.
- 기존 344개 일반 XSO 대응이 보존된다.
- 보조 XSO 71개가 v2 대응표에 포함된다.
- `AdolSleep`과 `OruhaMove`가 정확한 아카이브 엔트리에 대응한다.
- 통합 빌더가 일반·보조 XSO를 함께 처리한다.
- 할당 초과 시 전체 빌드가 중단된다.
- `s_0551`, `AdolSleep`, `OruhaMove` 번역이 하나의 ISO에 포함된다.
- 허용 범위 밖 ISO 변경이 0건이다.
- PPSSPP에서 세 대상의 번역과 이벤트 진행이 정상이다.
- 전체 테스트와 Python 바이트코드 컴파일이 통과한다.
- 원본 ISO와 기존 패치 ISO는 변경되지 않는다.
- 결과 문서와 정리 대상 중간 ISO가 기록된다.

## 중단 및 재확인 조건

- 새 할당 계산으로 기존 성공 패치의 대상 엔트리가 초과 상태가 됨
- 데이터 엔트리 오프셋 중복·중첩이 발견됨
- 보조 XSO 수가 예상과 크게 다르고 포맷을 설명할 수 없음
- v2 대응에서 하나의 standalone XSO가 여러 런타임 엔트리와 모호하게 연결됨
- 번역 토큰·마크업 불일치
- 수정 `.xso.z`가 기존 할당을 초과함
- 아카이브 크기 증가·엔트리 재배치가 필요함
- ISO extent 이동 또는 크기 증가가 필요함
- 실행 코드 패치가 필요함
- 대상 외 데이터가 변경됨
- 인게임 이벤트 진행이 손상됨

## 후속 작업

023 완료 후 standalone 직접 로드 후보와 구조 변형 인물명 XSO는 별도 유형으로 처리한다. 보조 엔트리 지원을 일반화한 뒤에도 런타임 증거가 없는 변형 파일을 자동 번역 전파하지 않는다.
