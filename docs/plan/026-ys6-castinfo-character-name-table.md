## 배경

025에서 `s_9000/talkisha.xso.z`와 `s_hidden1/talkisha.xso.z`의 이샤 문자열을 각각 수정했지만 현재 대화창의 인물명은 일본어로 유지됐다. 또한 주인공 `アドル`은 전체 XSO 대사 카탈로그에서 한 건도 발견되지 않았다.

원본 ISO를 CP932 바이트 단위로 검색한 결과, 대화창 화자명은 개별 XSO가 아니라 공통 캐릭터 데이터 `castinfo.dat`에서 관리되는 것으로 확인됐다.

`castinfo.dat`는 다음 두 위치에 동일한 바이트로 존재한다.

- standalone: `PSP_GAME/USRDIR/data/misc/castinfo.dat`
- 아카이브: `PSP_GAME/USRDIR/data/arc/init.bin` 엔트리 8 `castinfo.dat`

확인 정보:

- 크기: 21,264바이트
- SHA-256: `B91C22FC17C6E39A7B9DA8800099A598FB89FEB8ED262112142DD20736E2C730`
- 두 사본: 바이트 단위 완전 일치
- `init.bin` 내부 엔트리 flags: `0x01000000`
- `init.bin` 내부 할당: 22,528바이트
- 이샤 레코드 식별자: `CAST_C240`
- 이샤 이름 필드 오프셋: `0x2D20`
- 이름 필드 크기: 32바이트
- 원문: CP932 `イーシャ` 뒤 NUL 패딩

ISO에서 발견된 `アドル` 두 건은 `ブラックアドル` 레코드에 포함된 문자열로 일반 주인공 화자명이 아니다. 주인공 이름은 캐릭터 이름을 표시하지 않거나 별도의 플레이어명 시스템을 사용할 가능성이 있으므로 이번 단계에서는 임의 수정하지 않는다.

## 목표

1. `castinfo.dat` 고정 레코드 구조를 안전하게 파싱·검증한다.
2. `CAST_C240`의 이름 필드만 `이샤`로 교체한다.
3. standalone과 `init.bin` 내부 사본을 동일하게 수정한다.
4. 기존 025 누적 번역과 글리프 설정을 유지한 새 ISO를 생성한다.
5. 현재 접근 가능한 대화창에서 이샤 이름의 한글 출력을 확인한다.
6. 향후 다른 인물명을 같은 테이블에서 처리할 수 있는 재사용 가능한 스크립트를 마련한다.

## 범위

이번 단계에서 수정하는 항목:

- `CAST_C240` 이름: `イーシャ` → `이샤`
- `data/misc/castinfo.dat`
- `data/arc/init.bin` 내부 `castinfo.dat`
- 누적 EBOOT 및 기존 025 번역 대상 유지

이번 단계에서 제외하는 항목:

- `ブラックアドル` 및 기타 아돌 관련 레코드
- 전체 인물명 일괄 번역
- `invinfo.dat`, `effectdef.txt`의 이샤 문자열
- 사용자가 번역하지 않은 캐릭터명 자동 번역
- 플레이어 이름 입력 또는 세이브 데이터 이름
- 개별 `talk*.xso`의 추가 수정

사용자 확인 사항:

- `ブラックアドル`은 챌린지용 특수 캐릭터 또는 몬스터 계열 명칭으로 보이며 실제 캐릭터 명칭 자체는 맞다.
- 별도 대화를 진행하는 대상은 아니므로 이번 화자명 검증과 수정 범위에서는 제외한다.
- 사용자가 026 구현 진행을 승인했다.

## 원본 및 기존 결과 보호

- 원본 ISO는 읽기 전용으로 유지한다.
- 원본 SHA-256 `0133DC75EEEFB7E1864180C88E486D2EEBE9AE3D1DBFA990BEF57E28BAAE082B`를 전후 확인한다.
- 기존 025 ISO들을 덮어쓰지 않는다.
- 사용자 번역 정본을 수정하지 않는다.
- 작업 경로는 `/.work/ys6-castinfo-character-name-table`로 분리한다.
- 새 ISO는 `/patched/026-castinfo-character-name-table`에 한 개만 생성한다.
- 실패 시 `.partial` 파일을 삭제하고 기존 결과는 유지한다.

## 1단계: castinfo 구조 분석 및 검증기 작성

Python 비GUI 스크립트를 다음 경로에 작성한다.

- `/tools/scripts/ys6_castinfo.py`

지원 기능:

- `inspect`: 캐릭터 레코드 식별자와 이름 필드 목록 출력
- `patch`: 명시한 레코드의 이름 필드 교체
- `verify`: 수정 전후 구조·대상 외 바이트 보존 검사

초기 구조 판정은 `CAST_*` 식별자와 인접한 32바이트 NUL 종료 이름 필드를 기준으로 한다. 레코드 크기나 배치가 완전히 고정됐다고 추정하지 않고 실제 파일의 반복 패턴을 분석해 검증한다.

## 2단계: 이름 인코딩 방식

기존 CP932 이름 필드에는 게임의 한글 매핑 코드가 없으므로 `이샤`를 024~025에서 사용한 2바이트 게임 코드로 인코딩한다.

검증:

- `이`, `샤`가 현재 025 글리프 매핑에 존재
- 각 코드가 EBOOT 글리프 테이블의 실제 슬롯과 일치
- 인코딩 길이가 4바이트
- 뒤에 NUL을 추가하고 32바이트 전체를 0으로 패딩
- 필드 크기 증가 없음
- 원문 필드 밖 변경 없음

게임이 `castinfo.dat` 이름을 CP932 디코더가 아니라 자체 폰트 코드로 처리한다는 것은 인게임 검증으로 최종 확인한다. 한글 코드가 그대로 표시되지 않으면 별도 이름 렌더링 경로 분석이 필요하다.

## 3단계: 두 사본 수정

### standalone

- `PSP_GAME/USRDIR/data/misc/castinfo.dat`
- 원본 크기와 SHA-256 검증
- `CAST_C240` 및 `0x2D20`의 원문 필드 검증
- 수정 후 파일 크기 21,264바이트 유지

### init.bin 내부

- 엔트리 index 8
- 이름 `castinfo.dat`
- flags `0x01000000`
- 원본 payload SHA-256 검증
- 동일한 수정 `castinfo.dat`로 교체
- 아카이브 전체 크기와 엔트리 할당 유지
- 대상 외 엔트리 원시 바이트 보존

두 수정 사본의 SHA-256이 완전히 일치해야 한다.

## 4단계: 025 누적 빌드와 결합

기준은 최신 누적 검수본 115개와 왼쪽 정렬 글리프 192개다.

- 기존 025 EBOOT와 번역 XSO를 원본 ISO에서 재생성
- `init.bin` 수정본을 아카이브 교체 목록에 추가
- standalone `castinfo.dat`를 교체 목록에 추가
- `init.bin`이 기존 아카이브 캐시 처리와 충돌하지 않는지 확인
- 예상 교체 파일 개수와 실제 개수를 비교해 누락 차단

기존 `talkisha` 수정은 원인 분리 기록을 위해 누적 검수본에는 유지하되, 인물명 성공 여부는 `castinfo.dat` 수정으로 판정한다. 후속 정리 단계에서 불필요하다고 확정되면 별도로 제거할 수 있다.

## 5단계: 정적 검증

- 두 원본 `castinfo.dat` 사본의 동일성 확인
- 두 수정 사본의 동일성 확인
- `CAST_C240` 이름 필드가 정확한 한글 코드와 NUL 패딩인지 확인
- 수정 필드 밖 `castinfo.dat` 변경 0건
- `init.bin`에서 대상 엔트리 밖 변경 0건
- `init.bin` 크기·엔트리 index·flags·할당 유지
- standalone ISO extent LBA와 할당 유지
- ISO 허용 extent 및 길이 필드 밖 변경 0건
- 기존 025 번역 115개와 XSO 31개 유지
- 글리프 192개 모두 bbox 시작점 `x=1`
- 자동 테스트와 Python 컴파일 통과
- 원본 및 기존 025 ISO SHA-256 유지

## 6단계: 인게임 검증

현재 접근 가능한 동일한 이샤 대화 화면에서 확인한다.

- 화자명 `이샤` 출력
- 글리프 누락·깨짐 없음
- 이름 영역의 자간과 정렬
- 대사 본문 정상 유지
- 이벤트 진행 정상

결과 판정:

- 한글 출력 성공: `castinfo.dat`를 공통 화자명 정본으로 확정
- 일본어 유지: 다른 사본 또는 런타임 캐시/테이블 조사
- 깨진 코드 출력: `castinfo.dat` 전용 인코딩·렌더링 경로 조사

PPSSPP 메모리 추적이나 설정 변경은 기본적으로 수행하지 않는다. 정적 수정과 실제 출력이 다를 때만 별도 진단 계획을 작성한다.
