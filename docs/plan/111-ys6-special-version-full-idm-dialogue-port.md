# 111. Ys VI SPECIAL VERSION 전체 대응 IDM 대사 이식 계획

상태: 전체 시험 ISO 생성 완료 / 사용자 실기 확인 대기

## 배경

- 109번에서 SPECIAL VERSION의 IDM 241개를 전수 분석해 전체 6,341개 문자열 중 번역 원본과 안전하게 대응되는 4,127개를 확정했다.
- 당시 기존 폰트 안전 슬롯 한계 때문에 4,127개 중 1,650개만 적용하고 2,477개를 보류했다.
- 110번에서 기존 폰트 테이블을 별도 `PT_LOAD` 영역으로 옮겨 확장하는 방식을 구현했고, 사용자 실기에서 기존 대사와 신규 확장 글리프가 정상 표시되는 것을 확인했다.
- 109번 mapping revision 3에는 기존 339자와 안전 슬롯에 추가한 95자를 합쳐 434자가 고정되어 있다.
- 전체 4,127개 번역에는 revision 2 기준 신규 한글 607자가 필요했으므로, revision 3에 이미 포함된 95자를 제외하면 확장 테이블에 추가할 글자는 512자다.

## 목적

- 109번의 기존 한글 코드·폰트 인덱스 434개를 순서와 값 변경 없이 보존한다.
- 남은 신규 한글 512자를 110번에서 검증한 확장 테이블 뒤에 append한다.
- 대응이 확정된 IDM 번역 4,127개를 독립 IDM과 모든 런타임 아카이브 복사본에 동일하게 적용한다.
- 확장 BOOT/EBOOT과 IDM 자료를 포함한 전체 대사 시험 ISO를 별도 생성한다.
- 재현 가능한 mapping revision 4와 검증 보고서를 생성한다.

## 1. 입력 자료 고정

- 기반 ISO는 사용자 실기에서 기존 1,650개 IDM 번역이 확인된 109번 ISO로 고정한다.
- 다음 109번 산출물의 SHA-256과 구조를 다시 검증한다.
  - `hangul-mapping.json`
  - `resolution-report.json`
  - `idm-translations.json`
  - `runtime-map.json`
  - 수정 BOOT/EBOOT
- 110번 교정 증명본의 프로그램 헤더 순서와 PSP 재배치 엔트리를 기준 구현으로 사용한다.

## 2. append-only 전체 매핑 생성

- revision 3의 434개 행을 코드, 폰트 인덱스, 문자 및 순서까지 그대로 복사한다.
- 4,127개 번역에서 필요한 한글을 다시 계산하고 기존 434자를 제외한 집합이 정확히 512자인지 확인한다.
- 신규 문자는 Unicode 코드포인트 오름차순으로 고정한다.
- 신규 코드는 110번에서 실기 검증된 Shift-JIS 사용자 정의 영역을 사용한다.
- `0xF040`부터 유효한 trail byte 순서로 배정하되 다음과 충돌하지 않는지 검사한다.
  - 기존 폰트 코드 1,774개
  - revision 3의 434개 코드
  - 전체 원본 및 번역 IDM 바이트
  - 게임 제어 코드와 단일 바이트 문자
- 신규 폰트 인덱스는 기존 실제 테이블 1,774개 뒤에서 연속 배정한다.
- mapping revision 4의 총 한글 매핑 수는 946개가 되어야 한다.

## 3. 전체 확장 폰트 ELF 생성

- 기존 실제 폰트 테이블 1,774개를 바이트 단위로 보존해 신규 `PT_LOAD`에 복제한다.
- 신규 한글 512개의 16×14 1bpp, 28바이트 비트맵 레코드를 뒤에 append한다.
- 확장 테이블은 총 2,286개, 68,580바이트가 되어야 한다.
- 신규 `PT_LOAD`는 프로그램 헤더 index 2, 기존 PSP relocation 헤더는 index 3으로 유지한다.
- 세 주소 구성 쌍의 PSP relocation target segment를 모두 index 2로 유지한다.
- 세 검색 경로의 상한을 2,286으로 동일하게 수정한다.
- BOOT과 EBOOT은 각각 자신의 파일 끝에 맞춰 신규 세그먼트 파일 오프셋을 계산한다.
- 기존 데이터/BSS 끝 `0x355E90`과 신규 가상 주소 `0x360000`이 겹치지 않는지 다시 확인한다.

## 4. IDM 전체 이식 사전 검증

- `all_resolved` 4,127개만 적용 대상으로 사용한다.
- 모호 대응 282개, 미대응 665개, 번역 충돌 7개는 이번 범위에서 제외한다.
- 동일 대상 문자열에 서로 다른 번역이 배정되는지 다시 검사한다.
- 각 번역을 revision 4 매핑으로 인코딩하고 미지원 한글, 일본어 ruby 잔존 및 제어 코드 손상을 검사한다.
- 대상 IDM별 재구성 크기를 계산해 기존 standalone extent 할당량과 비교한다.
- 각 아카이브 복사본의 실제 엔트리 할당량과도 비교한다.
- 할당량을 넘는 IDM은 임의 절단하지 않고 별도 목록으로 중단 보고한다.

## 5. 독립 IDM 및 런타임 복사본 적용

- 241개 IDM 중 실제 번역 변경이 있는 자료만 재구성한다.
- 독립 `s_scene.idm`과 `runtime-map.json`에 기록된 모든 아카이브 복사본을 함께 갱신한다.
- 동일 IDM의 독립본과 모든 런타임 복사본이 바이트 단위로 같아야 한다.
- 아카이브 헤더, 엔트리 크기 및 후속 엔트리 오프셋은 기존 도구의 검증된 교체 방식으로 유지한다.
- 109번에서 이미 적용된 1,650개 번역도 새 매핑으로 재인코딩한 결과가 기존 바이트와 같은지 별도 비교한다.

## 6. 전체 시험 ISO 생성

- 109번 ISO를 읽기 전용 입력으로 사용하고 `/patched/111-special-version-full-idm-dialogue-port`에 새 ISO를 생성한다.
- 확장 BOOT/EBOOT은 110번과 같은 신규 ISO extent 배치 방식을 사용한다.
- 독립 IDM과 아카이브는 할당량 이내에서 기존 extent를 갱신한다.
- ISO9660 디렉터리 레코드의 little/big-endian extent 및 size를 함께 갱신한다.
- ISO 끝 확장 후 모든 volume descriptor의 volume space size를 실제 섹터 수와 맞춘다.
- 110번 실패본과 교정 증명본은 입력으로 재사용하거나 덮어쓰지 않는다.

## 7. 검증

- revision 3의 434개 매핑 행이 revision 4의 선두에서 완전히 동일한지 비교한다.
- 신규 512개 코드·폰트 인덱스·문자가 모두 고유한지 검사한다.
- 기존 1,774개 폰트 레코드가 신규 테이블 선두에서 바이트 단위로 동일한지 검사한다.
- 신규 512개 글리프가 공백이 아니며 16×14 셀을 넘지 않는지 검사한다.
- BOOT/EBOOT 프로그램 헤더 순서가 `PT_LOAD`, `PT_LOAD`, 신규 `PT_LOAD`, PSP relocation인지 확인한다.
- PSP 재배치 적용 후 세 폰트 테이블 주소가 모두 `0x360000`인지 확인한다.
- 세 검색 상한이 모두 2,286인지 확인한다.
- 4,127개 번역의 인코딩 바이트를 재추출 IDM에서 전수 비교한다.
- 독립 IDM과 모든 런타임 복사본을 전수 비교한다.
- ISO의 모든 수정 파일을 재추출해 작업본 SHA-256과 비교한다.
- 신규 BOOT/EBOOT extent가 다른 ISO 파일과 겹치지 않는지 검사한다.
- Python 구문 검사와 관련 기존 회귀 검사를 수행한다.

## 8. 사용자 실기 확인

- 게임 초반 `s_0551` 대사에서 기존 매핑 글자가 유지되는지 확인한다.
- 109번에서 보류되었던 대사 중 접근 가능한 장면을 선정해 신규 확장 글자를 확인한다.
- 시스템 메시지와 대화 전체가 사라지지 않고 정상 표시되는지 확인한다.
- 대화 종료, 맵 이동, 저장 및 불러오기가 정상 진행되는지 확인한다.
- 기존 세이브에 기록된 글자가 mapping revision 3과 동일하게 표시되는지 확인한다.

## 위험 및 중단 조건

- revision 3의 기존 434개 코드 또는 폰트 인덱스가 하나라도 바뀌면 ISO를 생성하지 않는다.
- 신규 사용자 정의 코드가 실제 원문·제어 바이트와 충돌하면 충돌 없는 코드 범위를 다시 선정하고 계획 문서를 갱신한다.
- 하나라도 IDM 또는 아카이브 할당량을 넘으면 해당 자료를 임의로 생략하지 않고 전체 목록과 대안을 먼저 보고한다.
- 110번에서 검증한 프로그램 헤더 순서나 재배치 결과가 달라지면 ISO를 생성하지 않는다.
- 기존 1,650개 번역 바이트가 예상과 다르면 109번 기반 상태부터 재검증한다.

## 사전 용량 검증 결과와 계획 변경

- 전체 4,127개 번역을 revision 4 후보 매핑으로 인코딩한 결과 대상 IDM은 131개이며, 그중 130개는 기존 할당량 안에 들어간다.
- `PSP_GAME/USRDIR/data/idm/s_40/s_4010/s_scene.idm` 한 건만 4,055바이트에서 4,160바이트로 증가해 standalone 할당량 4,096바이트를 64바이트 초과한다.
- 동일 IDM의 런타임 복사본은 `PSP_GAME/USRDIR/data/arc/s_4010.bin` index 6에 있고 할당량 역시 4,096바이트다.
- 아카이브에서 해당 IDM은 `0x800`에 있으며 다음 엔트리는 `0x1800`에서 시작한다. IDM 할당 구간을 한 섹터 늘려 6,144바이트로 만들고, `0x1800` 이후 모든 데이터 엔트리를 정확히 `0x800`바이트 뒤로 이동한다.
- 이동 대상 엔트리의 아카이브 테이블 offset 필드를 모두 `+0x800` 갱신하고, 각 payload와 엔트리 크기는 그대로 보존한다.
- 확장된 `s_4010.bin`은 기존 ISO 할당량을 넘으므로 BOOT/EBOOT과 마찬가지로 ISO 끝의 신규 extent에 배치한다.
- standalone `s_4010/s_scene.idm`도 신규 extent에 배치한다.
- 두 신규 extent의 directory record와 volume space size를 little/big-endian으로 갱신하고 다른 파일 extent와 비중첩인지 검사한다.
- 아카이브 확장 전후 모든 비대상 엔트리 payload SHA-256을 비교하고, 이동된 런타임 IDM이 standalone과 바이트 단위로 같은지 확인한다.

### 사용자 번역 축약 후 재검증

- 사용자가 `s_4010` 관련 번역 13개를 직접 축약·교정했다.
- 최신 `tools/config/dialogue-translations.json`을 기준으로 재구성한 `s_4010/s_scene.idm`은 4,087바이트다.
- standalone 및 아카이브 할당량 4,096바이트 안에 들어가며 남은 여유는 9바이트다.
- 따라서 위에서 조사한 standalone·아카이브 신규 extent 확장안은 적용하지 않는다.
- `s_4010.bin`을 포함한 모든 IDM과 아카이브는 기존 extent 및 기존 엔트리 offset을 유지하는 일반 교체 경로로 처리한다.

## 완료 기준

- append-only mapping revision 4가 기존 434자와 신규 512자를 포함한다.
- 총 2,286개 폰트 테이블과 세 검색 경로가 정적 검증을 통과한다.
- 대응 확정 번역 4,127개가 독립 IDM과 모든 런타임 복사본에 적용된다.
- 전체 시험 ISO가 재추출 및 구조 검증을 통과한다.
- 사용자가 실기에서 기존 글리프와 신규 확장 글리프가 포함된 대사를 확인할 수 있다.
