## 배경

계획 006에서 XSR/XSO 문자열 오프셋 테이블과 문자열 풀을 재구성하는 무수정 라운드트립이 실제 표본 31개에서 바이트 단위로 검증됐다. 현재 `ys6_xso.py`는 모든 문자열의 상대 오프셋을 다시 계산할 수 있지만, 안전장치로 교체 문자열의 바이트 길이가 원문과 같을 때만 변경을 허용한다.

계획 013~016에서는 이 동일 길이 제한 안에서 일본어와 한글 대사를 실제 게임에 적용했다. 전체 번역은 일본어 원문과 한국어 번역의 바이트 길이가 대부분 다르므로 다음 단계로 XSO 문자열 풀의 안전한 가변 길이 재조립을 검증해야 한다.

## 목표

1. `ys6_xso.py`의 기본 동일 길이 보호는 유지한다.
2. 명시적 옵션을 사용한 경우에만 한 문자열의 길이 증가·감소를 허용한다.
3. 변경된 문자열 뒤의 모든 상대 오프셋을 정확히 재계산한다.
4. 헤더와 명령 스트림, 문자열 개수 및 문자열 인덱스는 변경하지 않는다.
5. 수정 XSO를 `.z`로 재압축하고 기존 `s_0551.bin` 엔트리 할당 공간 안에 넣는다.
6. 22바이트보다 긴 한글 첫 대사를 PPSSPP에서 정상 출력해 런타임 버퍼와 오프셋 처리를 확인한다.

## 범위

이번 단계는 하나의 XSO 안에서 문자열 풀 크기가 달라지는 경우만 다룬다.

- 대상: `s_0551.xso.z`의 문자열 인덱스 35
- 원문: `どうしたの、イーシャ？`
- 원문 길이: 22바이트
- 시험문 후보: `한글출력테스트입니다입니다`
- 시험문 길이: 26바이트
- 예상 XSO 증가량: 4바이트

시험문은 계획 016에서 이미 인게임 검증한 10개 한글 매핑만 사용한다. 새로운 코드 슬롯이나 글리프 품질 변수를 추가하지 않고 가변 길이 처리만 검증한다.

## 범위에서 제외하는 작업

- 여러 XSO의 일괄 번역 반영
- 번역 CSV 편집기 또는 GUI
- XSO 명령 스트림과 문자열 인덱스 변경
- 문자열 추가·삭제
- `s_0551.bin` 내 다른 파일의 오프셋 이동
- 아카이브 전체 재배치 또는 크기 증가
- ISO 파일 재배치
- 전체 대사 번역

수정 `.xso.z`가 기존 2,048바이트 할당을 넘으면 이번 계획에서 아카이브를 확장하지 않는다.

## 원본 및 작업본 보호

- 원본 ISO `/roms/Ys VI - Napishtim no Hako (Japan).iso`는 읽기 전용으로 취급한다.
- 성공한 016 ISO는 변경하지 않는다.
- 분석·중간 XSO·압축 파일·아카이브 및 중간 ISO는 `/.work/ys6-variable-length-xso-poc`에 둔다.
- 최종 PoC ISO는 `/patched/017-variable-length-xso-poc`에 한 개만 둔다.
- 게임 원본 데이터와 복호화 EBOOT는 Git에 포함하지 않는다.
- 검증 완료 후 중간 ISO를 삭제한다.

## 1단계: XSO 재조립 불변식 정의

길이 변경 전후에 다음 조건을 검사한다.

- `XSR\0` 헤더와 헤더 미상 필드 동일
- 명령 워드 수와 명령 영역 전체 바이트 동일
- 문자열 개수와 각 문자열 인덱스 동일
- 오프셋 테이블 시작 위치와 문자열 풀 시작 위치 동일
- 상대 오프셋은 0에서 시작하고 엄격한 오름차순
- 대상 앞 문자열의 오프셋·원시 바이트 동일
- 대상 뒤 문자열의 오프셋은 누적 길이 차이만큼 이동
- 대상 외 모든 문자열의 원시 바이트, NUL 종료와 기존 패딩 길이 동일
- 재파싱 및 전체 문자열 목록 검증 성공

문자열 풀 끝에 별도 체크섬이나 크기 필드가 있는지 다시 확인한다. XSO 헤더에 전체 파일 크기 필드가 발견되면 함께 갱신하고 검증한다.

## 2단계: 명시적 가변 길이 옵션

기존 `rebuild_xso`와 `replace` 명령을 다음 원칙으로 보완한다.

- 기본 동작은 계속 동일 길이만 허용한다.
- `--allow-length-change`가 있을 때만 길이 차이를 허용한다.
- 결과에 원본 길이, 새 길이, 증감량, 원본·새 XSO 전체 크기를 출력한다.
- 영향받는 첫·마지막 문자열 인덱스와 오프셋 이동량을 보고한다.
- 기존 출력 덮어쓰기 보호를 유지한다.
- 원시 바이트 HEX 입력과 함께 사용할 수 있다.

잘못된 인덱스, NUL 포함 바이트, 잘린 CP932 선행 바이트 및 구조 검증 실패는 거부한다. 한글 전용 게임 코드는 CP932로 일본어 문자에 대응하므로 원시 바이트 자체의 구조 유효성을 기준으로 처리한다.

## 3단계: 단위 테스트

최소 다음을 추가한다.

- 기본 모드에서 길이 증가·감소 거부
- 명시적 옵션에서 길이 증가 성공
- 명시적 옵션에서 길이 감소 성공
- 대상 뒤 문자열의 오프셋이 정확한 증감량만큼 이동
- 대상 앞·뒤 문자열 원시 바이트 불변
- 명령 영역 불변
- 문자열 개수·인덱스 불변
- 재조립 결과 재파싱 성공
- 빈 문자열과 비어 있지 않은 문자열 간 교체
- 교체 바이트에 NUL이 포함되면 거부

전체 단위 테스트와 Python 바이트코드 컴파일을 수행한다.

## 4단계: 첫 대사 가변 길이 패치

계획 016의 매핑을 사용해 다음 원시 바이트를 생성한다.

- `한글출력테스트입니다입니다`
- 문자 수: 13자
- 게임 문자열 길이: 26바이트

수정 후 다음을 검증한다.

- 문자열 인덱스 35의 원시 바이트가 매핑과 일치
- 인덱스 0~34의 오프셋·내용 동일
- 인덱스 36~끝의 내용 동일, 오프셋만 +4바이트
- XSO 전체 크기 +4바이트
- 명령 영역 및 문자열 인덱스 참조 불변

## 5단계: 압축 및 아카이브 적용

- 수정 XSO를 기존 `ys6_z.py`로 zlib 레벨 9 압축한다.
- CRC32, 비압축 크기, zlib EOF 및 압축 해제 payload 동일성을 검증한다.
- 수정 `.xso.z`가 `s_0551.bin`의 기존 2,048바이트 할당 안에 들어가는지 확인한다.
- 기존 할당 안에 들어가면 크기 필드와 해당 할당 영역만 수정한다.
- 아카이브 크기와 다른 파일 오프셋은 유지한다.

압축 결과가 2,048바이트를 넘으면 구현을 중단하고 아카이브 재배치 계획을 별도로 작성한다.

## 6단계: PoC ISO 생성 및 검증

원본 ISO에서 다음 두 파일만 교체한다.

1. 계획 016과 동일한 다중 한글 글리프 적용 `EBOOT.BIN`
2. 가변 길이 대사가 포함된 `PSP_GAME/USRDIR/data/arc/s_0551.bin`

검증 항목:

- 원본 및 결과 ISO 크기·SHA-256
- 두 내부 파일의 재추출 SHA-256
- XSO 및 `.z` 재추출·재파싱
- 대사 원시 바이트와 한글 매핑 일치
- 원본 대비 허용 범위 밖 변경 0건
- 원본 ISO SHA-256 유지

## 7단계: PPSSPP 인게임 검증

- PPSSPP를 완전히 종료한 뒤 재실행
- 세이브 스테이트를 사용하지 않고 새 게임 시작
- 017 PoC ISO 직접 실행
- 첫 대사에 22바이트를 초과한 `한글출력테스트입니다입니다`가 끝까지 출력되는지 확인
- 다음 문자열이나 이벤트 진행이 손상되지 않는지 확인

첫 대사만 보이는 것으로 끝내지 않고 대사를 넘겨 다음 화면 또는 이벤트가 정상 진행되는지 확인해야 오프셋 이동 성공으로 판정한다.
