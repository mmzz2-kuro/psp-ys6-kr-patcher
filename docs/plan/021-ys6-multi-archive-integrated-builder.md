# Ys VI 다중 XSO·런타임 아카이브 통합 빌더 계획

## 상태

- 계획 작성: 완료
- 사용자 확인: 완료
- 구현: 완료
- 정적 검증: 완료
- 인게임 검증: `s_0551` 번역 29개와 후속 이벤트 정상 확인, 실제 다중 아카이브 표본은 번역 데이터 준비 전 보류
- 결과 문서: `/docs/result/021-ys6-multi-archive-integrated-builder.md`

## 배경

계획 019에서 `s_0551` 한 개의 번역을 다음 경로로 ISO에 적용하고 인게임 검증했다.

`검수 번역 → 문자 매핑·폰트 → XSO 재조립 → .z 압축 → 런타임 아카이브 → EBOOT·ISO`

계획 020에서는 원본 ISO의 런타임 아카이브 222개와 내부 XSO 344개를 전수 분석했다. 런타임 XSO 340개는 standalone XSO와 일대일 대응하며, 4개 런타임 XSO는 동일 payload를 사용하는 standalone 경로 15개와 대응한다. 손상된 런타임 XSO와 런타임 단독 XSO는 없었다.

현재 도구는 한 XSO와 한 아카이브를 수동으로 지정해야 한다. 게임 전체 번역을 확대하려면 번역 작업공간의 검수 완료 항목을 원본 XSO별로 묶고, 020 대응표에서 실제 런타임 엔트리를 찾아 여러 아카이브와 EBOOT를 하나의 ISO에 원자적으로 반영하는 통합 빌더가 필요하다.

## 목표

1. 검수 완료 번역을 여러 XSO에 걸쳐 자동으로 수집한다.
2. 원본 XSO SHA-256을 기준으로 020 런타임 대응표에서 수정 대상을 찾는다.
3. 동일 payload를 공유하는 standalone 경로의 번역 충돌을 빌드 전에 차단한다.
4. 전체 번역 문자 집합에 필요한 코드 매핑과 한글 글리프를 안정적으로 확장한다.
5. 여러 XSO를 재조립·압축하고 각 런타임 엔트리의 기존 할당 공간을 검사한다.
6. 여러 런타임 아카이브와 EBOOT를 원본 ISO 한 부에 일괄 반영한다.
7. 실패 시 부분 적용 ISO를 최종 결과로 남기지 않는 원자적 빌드를 구현한다.
8. 빌드 전 사전 검사와 빌드 후 검증을 사람이 읽을 수 있는 보고서로 남긴다.

## 중요한 범위 구분

이번 단계는 “여러 XSO와 아카이브를 안전하게 한 번에 빌드하는 기반”을 만드는 작업이다.

- 전체 7,424개 대사를 임의로 번역하지 않는다.
- 상태가 `reviewed`인 사용자 번역만 빌드 대상으로 삼는다.
- `standalone_only` XSO는 런타임 대상이 확인되지 않았으므로 ISO에 반영하지 않는다.
- 기존 엔트리 할당을 초과하는 XSO가 하나라도 있으면 전체 ISO 생성을 중단한다.
- 초과 엔트리를 건너뛰고 일부 번역만 조용히 반영하지 않는다.
- 아카이브 전체 재배치·확장과 ISO 파일 재배치는 별도 계획으로 분리한다.
- 메뉴·아이템·이미지·EBOOT 문자열 등 XSO 외 번역은 범위에 포함하지 않는다.
- 이번 단계의 사용자용 GUI는 만들지 않는다. 비GUI 통합 빌더를 `/tools/scripts`에 작성한다.

## 1단계: 통합 빌드 명세와 실행 모드

새 비GUI 스크립트 `/tools/scripts/ys6_integrated_build.py`를 작성한다.

실행 모드는 두 가지로 분리한다.

- `preflight`: 입력·대응·문자·압축·할당을 검사하고 보고서만 생성
- `build`: 동일한 사전 검사를 다시 통과한 뒤 EBOOT·아카이브·ISO 생성

`build`가 과거의 오래된 사전 검사 결과를 그대로 신뢰하지 않도록 한다. 모든 입력 파일의 SHA-256과 빌드 설정을 manifest에 기록하고, 실제 빌드 시 다시 계산한다.

출력 덮어쓰기는 명시적 `--overwrite` 옵션이 있을 때만 허용한다.

## 2단계: 번역 선택과 원문 검증

번역 작업공간에서 `status == "reviewed"`인 레코드만 선택한다.

각 레코드에 대해 다음을 확인한다.

- `iso_path`, `string_index`, `source_sha256` 키의 유효성
- 동일 키 중복 없음
- 번역문이 비어 있지 않음
- 원문 SHA-256이 카탈로그와 일치
- 문자열 인덱스가 원본 XSO 범위 안에 있음
- 원문의 토큰·마크업 보존 규칙 충족
- NUL과 지원하지 않는 제어문자 없음
- 실제 줄바꿈이 게임 `\n` 토큰으로 정규화됨

번역 원문은 수정하지 않고, 019에서 검증한 문장부호·말줄임표 정규화는 빌드 표시 문자열에만 적용한다.

선택 결과가 0건이면 빈 패치 ISO를 만들지 않고 중단한다.

## 3단계: 원본 XSO SHA-256별 그룹화

선택한 레코드를 standalone 경로가 아닌 원본 XSO payload SHA-256별로 그룹화한다.

각 그룹에는 다음을 둔다.

- 원본 XSO SHA-256
- 연결된 standalone ISO 경로
- 적용할 문자열 인덱스와 번역문
- 원본 문자열 SHA-256
- 020 대응표의 런타임 키
- 대응 상태

허용 대상:

- `exact_one_to_one`
- 충돌 검사를 통과한 `standalone_duplicate`

차단 대상:

- `standalone_only`
- `runtime_only`
- `runtime_duplicate`
- `many_to_many`
- `invalid`
- 대응표에 없는 해시

현재 020 결과에는 뒤의 네 런타임 모호 상태가 없지만, 향후 대응표 갱신에도 안전하도록 명시적으로 차단한다.

## 4단계: 동일 payload 번역 충돌 검사

동일 XSO payload를 공유하는 여러 standalone 경로에서 같은 문자열 인덱스에 번역이 존재할 수 있다.

- 같은 인덱스의 정규화된 번역 바이트가 같으면 하나로 병합한다.
- 한쪽에만 번역이 있으면 해당 인덱스 번역을 공통 런타임 payload에 적용한다는 사실을 보고서에 명시한다.
- 같은 인덱스의 번역문, 토큰 또는 마크업이 다르면 충돌로 중단한다.
- 서로 다른 인덱스의 번역은 하나의 XSO 변경 집합으로 합친다.

공유 런타임 payload를 수정하면 연결된 모든 게임 상황에 같은 변경이 노출될 수 있다. `standalone_duplicate` 그룹을 실제 빌드할 때는 영향받는 모든 standalone 경로를 manifest에 표시하고 인게임 검증 대상으로 포함한다.

## 5단계: 문자 집합·매핑·폰트 통합 빌드

전체 빌드 대상 번역문을 합쳐 고유 한글과 필요한 기호를 첫 등장 순서로 수집한다.

- 기존에 배정된 문자와 game code는 변경하지 않는다.
- 기존 매핑에 없는 문자만 016의 고유·미사용 안전 슬롯에 추가한다.
- 동일 문자를 둘 이상의 코드에 배정하지 않는다.
- 동일 코드를 둘 이상의 문자에 배정하지 않는다.
- CP932 전각 문장부호와 ASCII 제어 토큰은 새 한글 슬롯을 소비하지 않는다.
- 안전 슬롯이 부족하면 필요한 수와 부족분을 보고하고 중단한다.

폰트는 019와 동일하게 `C:/Windows/Fonts/gulim.ttc`, Gulim Regular, 12px, 16×12 1bpp, 안전 가시 폭 12px를 사용한다. `한`의 검증된 수동 패턴도 유지한다.

복호화 원본 EBOOT에서 전체 매핑의 글리프를 한 번에 생성하고 다음을 검증한다.

- 글리프 레코드 code와 매핑 일치
- 빈 글리프 없음
- 가시 폭 초과 없음
- 변경 범위가 배정 글리프 비트맵 영역으로 제한됨
- 동일 입력으로 재빌드 시 EBOOT SHA-256 동일

## 6단계: 다중 XSO 재조립

각 원본 XSO 해시 그룹을 한 번만 재조립한다.

- 그룹의 모든 번역을 한 번에 적용
- 문자열 개수와 명령 영역 보존
- 가변 길이에 따른 뒤쪽 상대 오프셋 누적 재계산
- 대상 외 문자열의 원시 바이트 보존
- 결과 XSO 재파싱
- 대상 문자열의 인코딩 바이트 역검증
- 대상 뒤의 문자열 및 마지막 문자열까지 구조 검증

보고서에는 XSO별 원본·수정 크기, 문자열별 길이 증감, 전체 증감 및 SHA-256을 기록한다.

## 7단계: 압축 및 할당 사전 검사

수정 XSO를 계획 019와 동일한 Ys VI `.z` 형식과 zlib 레벨 9로 압축한다.

검증 항목:

- 헤더 CRC32와 비압축 크기
- zlib EOF와 trailing data 없음
- 재해제 payload가 수정 XSO와 일치
- 압축 컨테이너 SHA-256
- 020 대응표의 런타임 엔트리 할당 크기
- 수정 압축 크기와 남은 공간

판정은 전체 빌드에 대해 원자적으로 수행한다.

- 모든 수정 `.xso.z`가 기존 할당 이내: 다음 단계 진행
- 하나라도 할당 초과: 초과 목록과 필요 크기를 기록하고 전체 ISO 생성 중단

초과 파일을 제외하고 나머지만 반영하는 옵션은 이번 단계에서 제공하지 않는다.

## 8단계: 다중 런타임 아카이브 생성

수정 XSO를 런타임 아카이브별로 그룹화한다.

- 각 원본 아카이브는 원본 ISO에서 한 번만 읽는다.
- 같은 아카이브에 여러 XSO가 있으면 메모리 작업본에 모두 적용한다.
- 엔트리 크기 필드와 데이터·패딩만 갱신한다.
- 파일 테이블 크기, 다른 엔트리의 오프셋과 아카이브 전체 크기는 유지한다.
- 모든 교체 후 아카이브를 다시 파싱한다.
- 수정 엔트리 재추출 SHA-256이 준비한 `.xso.z`와 일치하는지 확인한다.
- 대상 외 엔트리의 원시 데이터 SHA-256이 원본과 같은지 확인한다.

중간 아카이브는 `/.work/ys6-multi-archive-builder/archives`에 둔다.

## 9단계: 다중 파일 ISO 패처

기존 `ys6_iso_patch.py`의 단일 파일 교체 로직을 재사용하되, 여러 파일을 한 번의 원본 ISO 복사에 적용하는 기능을 구현한다. 별도 `/tools/scripts/ys6_iso_multi_patch.py`로 분리하거나 기존 스크립트에 안전한 다중 모드를 추가할 수 있다.

교체 대상:

1. 전체 글리프가 포함된 `PSP_GAME/SYSDIR/EBOOT.BIN`
2. 수정 XSO를 포함하는 각 `PSP_GAME/USRDIR/data/arc/*.bin`

요구 조건:

- 원본 ISO를 작업용 ISO로 한 번만 복사
- manifest에 선언된 파일만 교체
- 각 ISO 파일의 원본 크기·SHA-256 확인
- 기존 ISO extent 할당 안에서만 교체
- 디렉터리 레코드의 LE/BE 크기 필드 동시 갱신
- 각 대상의 extent LBA 유지
- 교체 대상 간 extent 중첩 없음
- 오류 발생 시 최종 경로로 승격하지 않음
- 모든 검증 후 임시 ISO를 최종 경로로 원자적 이동

아카이브 크기는 원본과 동일하게 유지되므로 ISO 디렉터리 크기 필드를 불필요하게 변경하지 않는다. EBOOT도 원본과 동일한 크기를 유지한다.

## 10단계: 전체 정적 검증

최종 ISO에 대해 다음을 검사한다.

- ISO 크기와 SHA-256
- 내부 EBOOT 재추출 SHA-256
- 모든 수정 아카이브 재추출 SHA-256
- 각 아카이브의 수정 `.xso.z` 재추출·해제·XSO 재파싱
- 모든 검수 번역의 원시 바이트 역검증
- 대상 외 아카이브 엔트리 보존
- EBOOT 글리프 매핑과 비트맵 일치
- 원본 대비 허용된 EBOOT·아카이브 extent 밖 변경 0건
- 원본 ISO SHA-256 재확인
- 전체 단위 테스트와 Python 바이트코드 컴파일

최종 manifest에는 입력·출력 SHA-256, 번역 수, XSO 수, 아카이브 수, 글리프 수, 할당 여유와 검증 결과를 기록한다.

## 11단계: 회귀 및 인게임 검증

최소 회귀 표본으로 계획 019의 번역 9개를 통합 빌더 입력에 사용한다.

- 통합 빌더가 `s_0551` 런타임 키를 자동 선택하는지 확인
- 인덱스 35~43의 번역과 문장부호 정규화가 019 결과와 일치하는지 확인
- PPSSPP 완전 종료 후 새 게임으로 오프닝 9개 대사 확인
- 줄바꿈, 말줄임표 간격과 이벤트 진행 확인

실제 검수 번역이 둘 이상의 런타임 XSO 또는 아카이브에 존재하는 경우 추가로 다음을 확인한다.

- 서로 다른 XSO의 번역이 모두 ISO에 포함됨
- 서로 다른 아카이브의 대사가 각각 정상 출력됨
- 한쪽 이벤트 검증이 다른 아카이브의 정상 동작을 대신하지 않음

현재 번역 작업공간에 인게임 접근 가능한 다중 아카이브 검수 번역이 없다면 임의 번역을 만들지 않는다. 이 경우 021에서는 정적 다중 아카이브 빌드 기능과 019 회귀를 완료하고, 실제 다중 아카이브 인게임 검증은 사용자가 다음 번역 묶음을 작성한 뒤 결과 문서의 보류 항목으로 명확히 남긴다.

## 완료 조건

- 검수 완료 번역만 자동 선택된다.
- 번역 원문 SHA-256, 토큰, 마크업 및 인덱스가 검증된다.
- 번역이 원본 XSO SHA-256별로 그룹화되고 020 런타임 키에 연결된다.
- 동일 payload 중복 그룹의 번역 충돌이 차단된다.
- 기존 문자 매핑을 보존하면서 필요한 새 글리프만 안정적으로 추가된다.
- 여러 XSO의 가변 길이 문자열이 올바르게 재조립된다.
- 모든 수정 `.xso.z`가 재해제·역검증된다.
- 할당 초과가 하나라도 있으면 전체 ISO 생성이 중단된다.
- 같은 아카이브의 여러 XSO를 한 작업본에 적용할 수 있다.
- 여러 아카이브와 EBOOT가 원본 ISO 한 부에 반영된다.
- 빌드 실패 시 불완전한 최종 ISO가 남지 않는다.
- 최종 ISO의 허용 범위 밖 변경이 0건이다.
- 019 오프닝 대사와 이벤트가 회귀 검증을 통과한다.
- 실제 다중 아카이브 검수 번역이 준비돼 있다면 각 아카이브의 인게임 검증을 통과한다.
- 전체 테스트와 Python 바이트코드 컴파일이 통과한다.
- 원본 ISO가 변경되지 않는다.
- 중간 ISO가 정리되고 결과 문서가 작성된다.

## 중단 및 재확인 조건

다음 중 하나가 발생하면 자동 우회하지 않고 계획을 갱신한 뒤 사용자에게 확인받는다.

- 020 대응표 또는 원본 ISO SHA-256 불일치
- 번역 원문의 SHA-256·토큰·마크업 충돌
- 동일 payload 공유 경로의 번역 충돌
- `standalone_only` 또는 모호한 런타임 대응에 번역이 존재함
- 필요한 한글·기호에 안전한 글리프 슬롯이 부족함
- 수정 `.xso.z` 하나라도 기존 엔트리 할당을 초과함
- 아카이브 엔트리 오프셋 이동 또는 전체 크기 증가가 필요함
- ISO 파일 extent 이동 또는 ISO 크기 증가가 필요함
- EBOOT 실행 코드 패치가 필요함
- 대상 외 XSO·아카이브 엔트리·ISO 범위가 변경됨
- 인게임에서 대사 또는 이벤트 진행 손상이 확인됨

## 후속 작업

021 결과에서 실제 할당 초과 사례가 확인되면 그 목록과 필요한 증가량을 근거로 아카이브 전체 재배치 계획을 별도로 작성한다. 통합 빌더가 안정화된 뒤에는 `/tools`의 사용자용 Python GUI 한글패치 도구가 이 빌더를 호출하도록 연결할 수 있다.

## 추가 번역 적용 범위 (2026-08-12)

사용자가 전체 번역 작업공간에 52개 번역을 추가했다. 읽기 전용 검사 결과 21개 XSO에 분포하며, 현재 020 대응표에서 런타임 위치가 확정된 것은 `s_0551.xso.z`의 번역 29개뿐이다.

- 적용 후보: `s_0551.xso.z` 인덱스 35~51, 53~64의 번역 29개
- 제외: 인덱스 52는 번역문이 없으므로 원문 유지
- 보존: `talkkebin`, `talktokusa`, `oruhamove`, `s_hidden1`의 번역 23개

추가 처리 절차:

1. 전체 번역 작업공간을 SHA-256과 함께 백업한다.
2. 사용자 정본은 수정하지 않고 `s_0551`의 번역된 29개만 별도 검수 JSON으로 복사한다.
3. 실제 CRLF/LF 줄바꿈을 게임의 리터럴 `\n` 토큰으로 변환한다.
4. 복사본만 `reviewed`로 바꾸고 원문 해시·토큰·마크업을 검증한다.
5. 021 `preflight`로 XSO 재조립, 글리프 수, 압축 크기와 2,048바이트 할당을 검사한다.
6. 할당을 통과하면 별도 021 ISO를 갱신하고 정적 검증한다.
7. PPSSPP에서 기존 9개와 신규 20개 대사 및 이후 이벤트를 확인한다.

검수 입력 준비나 사전 빌드에서 오류 또는 할당 초과가 발생하면 ISO를 갱신하지 않고 결과를 보고한다.
