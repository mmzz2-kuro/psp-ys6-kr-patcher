# 068. Ys VI 저장·불러오기 지역명 문자열 탐색 계획

상태: 완료

## 배경

- 저장 및 불러오기 목록 오른쪽에 저장 지점 명칭이 일본어로 표시된다.
- 확인된 예시는 다음과 같다.
  - `レダの集落`
  - `祈りの泉`
- 화면상 기존 게임 글꼴로 렌더링된 문자열처럼 보여 이미지 리소스보다는 지역 ID에
  대응하는 문자열 테이블 또는 세이브 데이터 문자열일 가능성이 있다.

## 목표

- 두 일본어 지역명의 실제 저장 위치와 인코딩을 찾는다.
- 저장 시 기록되는 값인지, 불러오기 화면에서 지역 ID를 이름으로 변환하는지
  구분한다.
- 한글 번역을 적용해야 하는 원본 리소스와 런타임 복사본 범위를 확정한다.

## 분석 계획

1. 문자열 후보 바이트를 준비한다.
   - Shift-JIS/CP932
   - UTF-8 및 UTF-16LE/BE
   - 프로젝트의 Ys VI 전용 문자 인코딩·문자 매핑 형식
2. 원본 ISO 전체와 주요 파일에서 두 문자열의 바이트 패턴을 검색한다.
   - `EBOOT.BIN`
   - 독립 XSO 및 압축 컨테이너
   - `init.bin`과 맵·메뉴 아카이브
   - 기타 바이너리 문자열 테이블
3. 압축된 `.z` 컨테이너는 해제된 payload에서도 검색한다.
4. 기존 대사 카탈로그와 비대사 문자열 조사 결과에 동일 문구 또는 관련 지역명
   목록이 있는지 확인한다.
5. 접근 가능한 실제 세이브 데이터가 있으면 동일 바이트 패턴과 지역 ID 후보를
   비교한다. 세이브 데이터가 저장소에 없다면 ISO 내부 조사 결과로 저장 시점과
   표시 시점 구조를 추론한다.
6. 발견된 후보 주변의 연속 문자열을 추출해 전체 저장 지점 명칭 테이블인지
   확인한다.
7. 코드 또는 명령 참조를 분석해 다음을 구분한다.
   - 저장 파일에 이름 문자열 자체를 기록
   - 저장 파일에는 숫자/지역 ID만 기록하고 UI에서 이름을 조회
8. 동일 리소스가 독립 파일과 아카이브에 중복되면 모든 런타임 복사본을 식별한다.

## 산출물

- 문자열 검색 결과와 후보 파일·오프셋
- 인코딩 판정 근거
- 저장/불러오기 표시 흐름에 대한 결론
- 번역 적용 대상과 필요한 패치 방식
- 후속 구현이 필요하면 별도 구현 계획의 범위
- `docs/result/068-ys6-save-load-location-name-discovery.md`

## 주의 사항

- 이번 단계는 탐색과 분석만 수행한다.
- 원본 ISO, 세이브 데이터, EBOOT 및 패치 파일은 수정하지 않는다.
- 대용량 임시 추출물이 필요하면 `tools/patchdata/work` 아래에 두고 결과 문서에
  정리 대상을 기록한다.

## 완료 기준

- 두 예시 지역명 중 최소 하나의 저장 위치 또는 생성 경로를 입증한다.
- 직접 문자열 검색으로 나오지 않으면 사용된 별도 인코딩·압축·ID 조회 구조를
  근거와 함께 좁힌다.
- 한글화를 위한 다음 구현 범위를 결정할 수 있을 정도로 대상과 위험을 정리한다.
