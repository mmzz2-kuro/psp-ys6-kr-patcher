# 110. Ys VI SPECIAL VERSION 한글 폰트 테이블 확장 계획

상태: 최소 확장 증명 실기 확인 완료 / 전체 확장 적용 대기

## 배경

- 109번에서 SPECIAL VERSION IDM 번역 4,127개를 안전하게 대응했지만 기존 폰트 안전 슬롯은 434개뿐이다.
- 106번 mapping revision 2의 339자와 109번 신규 95자를 합쳐 안전 슬롯 434개를 모두 사용했다.
- 보류된 안전 대응 번역 2,477개를 적용하려면 신규 한글 607자가 추가로 필요하다.
- 후속 검색 루틴 분석에서 SPECIAL VERSION의 실제 폰트 테이블은 파일 오프셋 `0x15EAD0`에서 시작하고 30바이트 레코드 1,774개로 구성됨을 확인했다. 기존에 확인한 `0x15EB2A`는 앞쪽 내부 레코드 3개를 제외한 화면 글리프 구간이다.
- 기존 테이블 끝 `0x16BAB4` 뒤에는 즉시 다른 실행 데이터가 이어져 있어 제자리 확장이 불가능하다.
- 실행 파일 내부의 가장 큰 연속 0바이트 영역은 1,085바이트로, 필요한 약 18,210바이트를 저장할 수 없다.
- 현재 EBOOT ISO extent의 여유도 약 1KB이므로 단순 파일 확장만으로는 ISO에 들어가지 않는다.

## 목적

- 기존 일본어 폰트 테이블과 109번 매핑 434개를 그대로 보존한다.
- 신규 한글 최소 607자를 저장할 별도 확장 글리프 테이블을 ELF의 새로운 로드 영역에 추가한다.
- 글리프 검색 루틴이 사용하는 테이블 전체를 새 로드 영역으로 복제하고 신규 레코드를 뒤에 append한 뒤, 세 검색 경로의 시작 주소와 상한을 새 테이블에 맞게 수정한다.
- 확장된 BOOT/EBOOT을 SPECIAL VERSION ISO의 새 extent에 안전하게 배치한다.
- 작은 증명 ISO로 검색 루틴과 확장 글리프 출력을 먼저 확인한 뒤 전체 IDM 번역 이식 가능성을 검증한다.

## 1. 폰트 검색 루틴 식별

- 기존 폰트 테이블의 메모리 주소와 1,774개 레코드 수를 참조하는 MIPS 코드를 찾는다.
- 다음 동작을 정적으로 분석한다.
  - 게임 문자열의 2바이트 코드 입력
  - 폰트 레코드 코드 비교
  - 선형 또는 이진 검색 방식
  - 검색 실패 처리
  - 비트맵 주소 반환 방식
- 동일 테이블을 사용하는 렌더링 경로가 여러 개인지 확인한다.
- 대사, 메뉴 및 시스템 문자열이 같은 검색 함수를 사용하는지 교차 참조한다.
- 함수 진입 주소, 원본 명령어와 호출 지점을 보고서로 기록한다.

## 2. 확장 테이블 형식

- 기존과 동일한 30바이트 레코드를 사용한다.
  - 게임 코드 2바이트
  - 16×14 1bpp 비트맵 28바이트
- 확장 테이블에는 기존 1,771개 테이블에 없는 신규 코드만 넣는다.
- 코드 정렬이 검색 방식에 필요한 경우 정렬 순서를 유지한다.
- 테이블 앞에 필요하면 magic, 레코드 수와 크기를 가진 작은 헤더를 둔다.
- 109번 기존 mapping revision 3의 434개 코드·폰트 인덱스는 변경하지 않는다.
- 신규 코드는 CP932 원본 코드와 충돌하지 않는 별도 코드 범위를 조사해 배정한다.

## 3. ELF 확장 로드 영역

- 기존 두 `PT_LOAD` 영역과 PSP relocation 영역을 훼손하지 않고 새 글리프 데이터용 로드 영역을 추가한다.
- 우선안은 ELF 프로그램 헤더에 별도 읽기 전용 `PT_LOAD` 항목을 추가하는 것이다.
- 새 영역은 기존 메모리 구간과 겹치지 않는 정렬된 가상 주소에 배치한다.
- 다음 값을 검증한다.
  - 파일 오프셋 및 가상 주소 정렬
  - `p_filesz`, `p_memsz`와 ELF 전체 크기
  - 프로그램 헤더 수와 남은 헤더 공간
  - PSP relocation 데이터 및 section header 오프셋
  - 게임 메모리 범위와 충돌 여부
- 새 `PT_LOAD`가 PSP 로더에서 허용되지 않으면 두 번째 대안으로 기존 데이터 `PT_LOAD` 확장과 뒤쪽 relocation 데이터 이동을 조사한다.

## 4. 검색 루틴 확장

- 기존 테이블 조회 결과가 성공하면 기존 동작을 그대로 유지한다.
- 기존 테이블에서 코드를 찾지 못한 경우에만 확장 테이블을 조회한다.
- 검색 실패 시 원래 게임의 대체 글리프 동작을 유지한다.
- 코드 공간이 부족하면 가까운 함수의 안전한 코드 영역에 trampoline을 두고 새 로드 영역의 검색 코드로 분기한다.
- 수정 명령어, 분기 범위, delay slot과 레지스터 보존을 검증한다.
- 기존 일본어 코드 전체에 대해 검색 결과 주소가 원본과 동일한지 자동 비교한다.

## 5. 확장 실행 파일 ISO 배치

- 기존 EBOOT extent는 확장 크기를 수용하지 못하므로 고정 extent 교체 방식은 사용하지 않는다.
- 원본 ISO의 파일 배치 끝 또는 확인된 연속 여유 영역에 확장 BOOT/EBOOT용 새 extent를 할당한다.
- ISO9660 directory record의 다음 값을 새 위치와 크기로 갱신한다.
  - little-endian extent LBA 및 size
  - big-endian extent LBA 및 size
- 원본 extent는 덮어쓰지 않으며 다른 파일과 겹치지 않는지 전역 검사한다.
- 출력 ISO를 다시 열어 BOOT/EBOOT을 재추출하고 작업본과 비교한다.
- ISO 허용 범위는 새 extent, directory record와 필요한 volume size 필드로 제한한다.

## 6. 최소 확장 증명

- 기존 109번 ISO를 기준 작업본으로 사용한다.
- 기존 안전 슬롯에 없는 신규 한글 16~32자를 확장 테이블에만 넣는다.
- 초반 IDM 대사 한두 문장을 해당 신규 코드로 인코딩해 바로 확인할 수 있게 한다.
- 다음 항목을 실기에서 확인한다.
  - 정상 부팅
  - 기존 109번 한글 출력 유지
  - 확장 테이블의 신규 한글 출력
  - 기존 일본어 글리프 보존
  - 대화 종료와 맵 전환 정상 동작
- 최소 증명이 실패하면 전체 607자 테이블은 만들지 않고 원인을 분석한다.

## 7. 전체 확장 자료 생성

- 최소 증명이 성공하면 109번에서 보류된 2,477개 번역에 필요한 신규 607자를 확장 테이블에 배정한다.
- mapping revision을 4로 올리고 기존 434개 뒤에 append-only로 추가한다.
- 전체 확장 글리프 아틀라스와 코드·주소 보고서를 생성한다.
- 전체 IDM 4,127개 적용 시 필요한 실행 파일 및 ISO 크기와 할당 공간을 사전 검증한다.
- 전체 번역 ISO 생성은 최소 확장 실기 확인 후 후속 단계에서 진행한다.

## 검증

- 기존 1,771개 폰트 코드의 검색 결과 주소를 원본과 비교한다.
- 기존 109번 434개 글리프 비트맵과 코드 배정이 불변인지 확인한다.
- 모든 확장 코드가 고유하고 기존 코드와 충돌하지 않는지 확인한다.
- 확장 비트맵이 16×14 셀을 넘거나 공백이 아닌지 검사한다.
- 수정 MIPS 명령의 분기 대상, delay slot과 레지스터 보존을 확인한다.
- ELF 프로그램 헤더, load segment와 relocation 영역을 다시 파싱한다.
- 확장 BOOT/EBOOT을 ISO에서 재추출해 SHA-256을 비교한다.
- ISO 파일 extent가 중첩되지 않는지 전수 검사한다.

## 위험 및 중단 조건

- PSP 로더가 새 `PT_LOAD` 영역을 적재하지 않으면 해당 방식을 중단하고 기존 데이터 segment 확장 방식을 재검토한다.
- 폰트 검색 경로가 여러 개이고 모두 안전하게 수정할 수 없으면 일부 UI에 확장 문자가 표시되지 않을 수 있다.
- 신규 코드가 게임 제어 코드 또는 문자열 파서와 충돌하면 해당 코드 범위를 사용하지 않는다.
- 확장 실행 파일을 새 ISO extent에 배치한 결과 부팅하지 않으면 원본 extent 방식과 ISO 재구성 방식을 분리해 원인을 확인한다.
- 기존 109번 글리프 또는 일본어 검색 결과가 하나라도 바뀌면 테스트 ISO를 생성하지 않는다.

## 1차 실기 실패 및 교정 계획

- 1차 증명 ISO에서는 신규 `PT_LOAD`를 PSP relocation 프로그램 헤더 뒤의 index 3에 추가했지만, 여섯 재배치 엔트리의 target segment는 index 2로 기록했다.
- PSP 재배치의 target segment가 프로그램 헤더 index를 따르는 경우 index 2는 신규 폰트 영역이 아니라 `0x700000A0` PSP relocation 헤더를 가리킨다.
- 이 경우 세 폰트 검색 경로의 테이블 주소가 `0x360000`으로 보정되지 않아 시스템 메시지와 대사를 포함한 모든 글리프 검색이 실패하며, 사용자 실기 증상과 일치한다.
- 기존 PSP relocation 헤더를 빈 헤더 슬롯 index 3으로 이동하고 신규 `PT_LOAD`를 index 2에 배치한다.
- 재배치 target segment 2는 유지하되, 검증 도구도 `PT_LOAD`만 압축해서 번호를 매기지 않고 실제 프로그램 헤더 index를 기준으로 재배치를 적용하도록 보강한다.
- 교정본은 기존 1차 ISO를 덮어쓰지 않고 별도 파일명으로 생성하며, 부팅과 기존·신규 글리프 출력을 다시 실기 확인한다.

## 완료 기준

- 폰트 검색 루틴과 테이블 개수 참조가 확정된다.
- 확장 테이블을 포함한 ELF가 구조 검증을 통과한다.
- 기존 폰트 검색 결과와 109번 매핑이 완전히 보존된다.
- 최소 16개 이상의 확장 글리프가 기존 안전 슬롯 밖에서 배정된다.
- 새 extent를 사용하는 최소 증명 ISO가 생성되고 재추출 검증을 통과한다.
- 사용자가 실기에서 기존 및 확장 한글 출력과 정상 진행을 확인할 수 있다.
