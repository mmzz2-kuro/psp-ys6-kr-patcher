- 완료
- 사용자 승인: 2026-08-11

## 결론

- `talk*.xso.z`, `seltalk.xso.z`, `endtalk.xso.z`는 대사 및 이벤트 바이트코드 파일이 맞다.
- `.z` 해제 후 실제 매직은 확장자와 다른 `XSR\0`이다.
- XSR은 명령 워드, 문자열 상대 오프셋 테이블, NUL 종료 문자열 풀로 구성된다.
- 문자열 인코딩은 CP932(Shift-JIS 호환)다.
- 문자열 풀만 추출하는 것은 가능하지만, 안전한 재삽입을 위해서는 바이트코드의 문자열 참조 명령을 추가로 분석해야 한다.

## XSR 구조

### 헤더

| 오프셋 | 크기 | 확인 내용 |
|---:|---:|---|
| `0x00` | 4 | 매직 `58 53 52 00` (`XSR\0`) |
| `0x04` | 가변 | 버전·플래그 등으로 보이는 공통 헤더, 세부 의미 미확정 |
| `0x1C` | 4 | 명령 영역의 4바이트 워드 수, u32 little-endian |
| `0x20` | 4 | 문자열 수, u32 little-endian |
| `0x24` | 가변 | 바이트코드 명령 워드 배열 시작 |

### 계산식

```text
code_start   = 0x24
offset_table = code_start + code_word_count * 4
string_pool  = offset_table + string_count * 4
```

- `offset_table`에는 `string_count`개의 u32 little-endian 상대 오프셋이 있다.
- 각 상대 오프셋의 기준은 `string_pool`이다.
- 문자열은 CP932 바이트열이며 NUL로 끝난다.
- 파일 마지막 문자열 뒤에는 4바이트 정렬로 보이는 추가 NUL 패딩이 있을 수 있다.
- 모든 표본에서 명령 영역의 마지막 워드는 원시 바이트 `00 00 00 01`이었다. 종료 명령으로 추정되지만 의미는 아직 확정하지 않는다.

## 인코딩과 문자열 표기

- 일본어는 CP932로 정상 복원된다.
- 개행은 실제 LF가 아니라 ASCII 두 바이트 `5C 6E` (`\\n`)으로 저장된다.
- `\\x1`은 파일에서 ASCII 4바이트 `5C 78 31` 형태이며, 문맥상 플레이어 이름 삽입 토큰 후보다.
- 예: `やあ、\\x1君。\\nリモージュには着けたかい？`
- 캡션 제어 표본에는 일본어가 아닌 `map_name12` 같은 ASCII 문자열도 같은 문자열 풀에 저장된다.
- 따라서 추출기는 일본어 문자열만 고르는 방식이 아니라 문자열 테이블의 모든 엔트리를 보존해야 한다.

## 메시지 경계

- 메시지 경계는 문자열 오프셋 테이블과 NUL 종료자로 이중 확인할 수 있다.
- 다음 엔트리의 상대 오프셋이 현재 엔트리의 저장 범위 상한이 된다.
- 마지막 엔트리는 파일 끝까지가 상한이지만 최초 NUL 뒤의 정렬 패딩은 문자열 내용에서 제외해야 한다.
- 표본 5개, 총 63개 문자열에서 테이블 경계와 CP932 디코딩이 재현됐다.

## 바이트코드 및 재삽입 위험

- 명령 영역은 4바이트 단위이지만 명령별 인자 수가 달라 보이는 VM 구조다.
- 문자열 오프셋 테이블은 문자열 풀 상대값이므로 문자열 길이가 변하면 후속 오프셋을 재계산해야 한다.
- 바이트코드가 문자열을 테이블 인덱스로 참조하는지, 직접 오프셋으로 참조하는지는 아직 미확정이다.
- 선택지, 화자, 대기 및 분기 의미는 문자열 내용만으로 확정할 수 없다.
- 재삽입은 XSR 읽기→동일 바이트 재조립 라운드트립과 바이트코드 참조 분석 전에는 진행하면 안 된다.
