# Ys VI 한글 코드 매핑 및 다중 글리프 생성 기반 결과

## 상태

- 구현: 완료
- 정적 검증: 완료
- PPSSPP 인게임 검증: 성공

## 결론

Ys VI PSP의 기존 2바이트 문자 처리 구조를 유지하면서 여러 한글을 결정론적으로 배정하고, 복호화 EBOOT에 글리프를 일괄 삽입하는 기반을 구현했다. 대표 문구 `한글출력테스트입니다`의 10개 한글을 첫 대사에 적용했으며 사용자가 PPSSPP 새 게임에서 모든 글자가 정상 출력됨을 확인했다.

실행 코드, 폰트 레코드 순서 및 코드값은 수정하지 않았다. 대사에는 기존 폰트 테이블에 존재하면서 원본 추출 문자열에서 사용되지 않는 고유 CP932 코드 슬롯을 사용했다.

## 폰트 및 코드 사용 현황

복호화 EBOOT와 전체 XSO 카탈로그 7,424개 문자열을 결합해 조사했다.

| 항목 | 결과 |
|---|---:|
| 폰트 레코드 | 4,608개 |
| 고유 폰트 코드 | 3,692개 |
| 추출 문자열에서 사용된 2바이트 코드 | 1,524개 |
| 2바이트 코드 총 출현 횟수 | 106,580회 |
| 고유·미사용 안전 후보 | 2,136개 |
| 폰트에 없는 사용 코드 | 0개 |

폰트 테이블에는 `0x8145` 등 중복 코드 레코드가 다수 존재하므로 레코드 수만으로 슬롯을 배정하지 않는다. 이번 매핑은 다음 조건을 모두 만족하는 슬롯만 자동 선택한다.

- 추출 문자열 사용 횟수 0
- 폰트 테이블 내 코드 중복 없음
- CP932로 디코딩 가능한 기존 코드
- 기존 예약 코드와 충돌 없음

XSO 외부의 UI나 실행 파일 문자열까지 완전히 사용되지 않는다고 단정할 수는 없다. 이번 PoC는 첫 대사에서 안전성을 확인한 기반이며, 전체 번역 단계에서는 남은 일본어와 UI 범위를 함께 검증해야 한다.

| 출 | `0x98FA` | 4603 | 傅 |
| 력 | `0x98F9` | 4602 | 傚 |
| 테 | `0x98F8` | 4601 | 傀 |
| 스 | `0x98F7` | 4600 | 偸 |
| 트 | `0x98F6` | 4599 | 偬 |

| 니 | `0x98F4` | 4597 | 做 |

`한 → 0x98FC`는 계획 015와 호환되며, 나머지는 폰트 인덱스 역순으로 결정론적으로 배정했다. 매핑 정본은 UTF-8 CSV와 JSON으로 작업 폴더에 생성했다.

## 글리프 생성

- 원본 글꼴: `C:/Windows/Fonts/gulim.ttc`
- 글꼴 면: Gulim Regular, TTC 인덱스 0
- 생성 크기: 12px
- 게임 형식: 16×12, 1bpp, 글리프당 24바이트
- 실제 안전 가시 폭: 12px

자동 생성 글리프의 픽셀 경계가 x=12 이상으로 나가면 초과 폭만큼 왼쪽으로 이동한다. 계획 015에서 화면 검증한 `한`은 수동 패턴 재정의 기능으로 동일한 성공 도안을 사용했다. 나머지 9자는 Gulim 자동 생성과 12px 안전 폭 보정을 적용했으며 모두 인게임에서 정상 출력됐다.

## 대사 PoC

- 대상 아카이브: `PSP_GAME/USRDIR/data/arc/s_0551.bin`
- 내장 파일: `s_0551.xso.z`
- 문자열 인덱스: 35
- 원문: `どうしたの、イーシャ？`
- 시험 문구: `한글출력테스트입니다` + 전각 공백 1개
- 기존 및 교체 문자열 길이: 22바이트

## 남은 범위와 제약

- 현재 자동 배정 가능한 고유·미사용 후보는 2,136개다. 실제 완성 번역의 고유 한글·기호 수가 이를 넘으면 번역 완료 후 더는 필요하지 않은 일본어 슬롯을 회수하는 정책이 필요하다.
- 전체 번역에 필요한 문자 집합이 확정되기 전에는 모든 슬롯을 선점하지 않는다.
- 메뉴, 이미지, 영상 자막 및 XSO 외부 텍스트는 별도 조사 대상이다.
- 현재 XSO 교체는 같은 바이트 길이만 지원한다. 자연스러운 전체 번역에는 문자열 길이와 아카이브 재배치 방식을 다음 단계에서 설계해야 한다.
